# API Layer

## API layer — single request() funnel

[src/api.js](../../src/api.js) is a thin wrapper around `fetch()`. Every endpoint method goes through a single `request(method, path, { params, body, base, raw, asResponse })` function that injects Basic auth, logs the call, and parses the response. Errors propagate to the caller — there is no offline fallback. `{ asResponse: true }` short-circuits the parse step and returns the raw `Response` so binary callers (e.g. `api.getDeploymentResource`) can pick `.blob()` / `.arrayBuffer()`; mutually exclusive with `raw`.

Two important details:

- **DMN lives at a different URL prefix.** Flowable's BPMN/runtime/identity endpoints are under `/flowable-rest/service`, but DMN sits at `/flowable-rest/dmn-api`. The `dmnBase()` helper derives the DMN root from the configured base URL. Pass `{ base: dmnBase() }` for any DMN call. **Story 34.1 generalized this convention (FR-59): the rewrite is now `connectionRoot()`-relative and per-connection-configurable.** `connectionRoot()` strips the configured `servicePath` suffix (default `/service`) from `cfg.baseUrl` to recover the deployment root; each `*Base()` helper appends its own configurable segment (`dmnBase = connectionRoot() + (cfg.dmnPath || "/dmn-api")`, plus `appBase` / `cmmnBase` for `/app-api` / `/cmmn-api`). All four prefixes (`servicePath` / `dmnPath` / `cmmnPath` / `appPath`) are optional per-`SavedConnection` overrides (`schemaVersion: 2`, lossless v1→v2 migration) surfaced via the collapsible `<SubAppPrefixFields>` group (the 2nd idPrefix-namespaced presentational extraction after `<AuthStrategyFields>`); blank → the standard default → byte-identical to the pre-34.1 `baseUrl.replace(/\/service\/?$/, "/dmn-api")`. The `request()` funnel is UNCHANGED — all derivation stays in the `*Base()` helpers. `cmmnBase()` is forward-reserved (no Flowatch CMMN consumer yet; FR-50).
- **`/identity/tenants` does not exist in flowable-rest 7.2.** `api.listTenants()` derives distinct tenant IDs from `/repository/deployments` instead.
- **Flowable job IDs are scoped to per-type namespaces** (Story 12.2). Executable jobs, timer jobs, and dead-letter jobs live in three SEPARATE URL namespaces with different valid action verbs and different stacktrace endpoints. `POST /management/jobs/{timerId}` returns 404; the `/management/timer-jobs/{id}` endpoint accepts `{action: "move"}` (fire-now) and `{action: "reschedule", dueDate: <iso>}`; `/management/deadletter-jobs/{id}` accepts `{action: "move"}`. Use the namespace-specific wrappers in [src/api.ts](../../src/api.ts) (`executeJob` / `executeTimerJob` / `rescheduleTimerJob` / `moveDeadLetterJob` plus three stacktrace variants). Full quirk listed as RC-11 in [docs/runtime-caveats.md](../runtime-caveats.md). The handler-side pattern is **tab-aware action-verb dispatch** (see component-patterns.md).

When adding a new endpoint, just add a wrapper in [api.js](../../src/api.js) and export it from the `api` object at the bottom of the file.

## Pluggable AuthStrategy seam

**Pluggable AuthStrategy seam (Story 28.1).** `request()` and `multipartFetch()` no longer hard-code Basic auth — both `await authStrategy.authorizationHeader()` (the strategy is the SINGLE header source for the funnel) and the 401 path calls `authStrategy.onUnauthorized?.()` (additive to the error — recovery side-channel, never swallows). The `AuthStrategy` interface (`kind` / `authorizationHeader(): Promise<string | null>` / optional `onUnauthorized()`) + the concrete classes live in [src/lib/auth-strategy.ts](../../src/lib/auth-strategy.ts) — NEW auth methods add a strategy class + a dispatcher entry; they NEVER re-edit the funnel. `BasicAuthStrategy` is the module default (reads `cfg.{username,password}` via a getter closure so `api.setConfig` / connection switches reflect without re-installing). `authorizationHeader()` is async BY DESIGN for OIDC's on-demand token refresh (Story 28.4 payoff); the `| null` return widens ADR-009's `Promise<string>` for the reserved no-auth / empty-token case (`null` → no `Authorization` header) — don't "fix" it back. The active strategy stays `BasicAuthStrategy` for the whole session until Story 28.2's `installStrategyForActiveConnection()` dispatcher swaps it per the active connection's `authStrategyConfig.kind`. Swap point: `api.setAuthStrategy(...)` / `api.getAuthStrategy()`. NFR-8 redaction is scheme-preserving (`Basic ***` / `Bearer ***`) and untouched. This is a genuine new architectural convention (not an N=k codification) — `AuthStrategy` family is N=1 concrete (Basic) at Story 28.1; Bearer (28.3) → N=2, OIDC (28.4) → N=3. **Bearer (Story 28.3, N=2):** `BearerAuthStrategy` produces `Bearer <token>` from the active connection's `authStrategyConfig.config.token` (live getter — re-paste without re-install; opaque token, NO `exp`/refresh — that's OIDC's job); empty token → `null` → no header → 401. It is the FIRST real `onUnauthorized` consumer — a 401 dispatches `OPEN_SETTINGS_AUTH` ([src/lib/nav-events.ts](../../src/lib/nav-events.ts)) via an injected callback, and the app listener opens `<SettingsModal>` at the Connection tab so the operator can locate and re-configure their active connection's auth via the Edit button (additive to the error — the screen still shows its ErrorBox). The Authentication tab was removed in Story 34.1 amendments. The dormancy note narrowed to OIDC-only (Bearer is now live). **OIDC (Story 28.4, N=3 — the last placeholder swap):** `OidcAuthStrategy.authorizationHeader()` is the async seam's payoff — it `await`s an INJECTED bridge accessor's `getToken()` (in-memory access token; `automaticSilentRenew` keeps it fresh) and returns `Bearer <access-token>` or `null`. The accessor is published by `OidcTokenBridge` (`useAuth()`) into the plain-TS singleton in [src/lib/oidc-accessor.ts](../../src/lib/oidc-accessor.ts); the strategy reads it via the injected getter so [src/lib/auth-strategy.ts](../../src/lib/auth-strategy.ts) stays React-free. **`onUnauthorized()` does a DEBOUNCED (≤1 / 10 s) best-effort SILENT renew — it MUST NOT interactive-redirect (RC-18):** a Basic-only Flowable engine 401s every OIDC call, so `signinRedirect()` from the funnel would create an infinite redirect loop (call → 401 → redirect to IdP → back → 401 → …). Interactive sign-in is USER-initiated via the button in `<ManageConnectionsPanel>` (Connection tab) only. **The active strategy is installed at MODULE LOAD ([src/main.tsx](../../src/main.tsx) calls `installStrategyForActiveConnection()` before render)** — otherwise the earliest probe / nav-count calls fire under the module-default `BasicAuthStrategy` with empty creds (`Authorization: Basic Og==`) before app.tsx's mount effect swaps it. **NFR-11:** oidc-client-ts' DEFAULT `userStore` is `window.sessionStorage` (NOT in-memory!), so the provider passes an explicit `userStore: new WebStorageStateStore({ store: new InMemoryWebStorage() })` to keep tokens in the JS heap; the `stateStore` is LEFT as the default `localStorage` (the transient PKCE `code_verifier` MUST survive the redirect round-trip). Only `{issuer, clientId, scopes}` config persists (via Story 23.2). `getToken()` must NOT call `signinSilent()` per-request (it runs on every `api.*` call — would storm the IdP with iframes). `react-oidc-context` + `oidc-client-ts` are installed; the OIDC bundle is its own Vite `manualChunks` chunk + the provider ([src/lib/oidc-provider.tsx](../../src/lib/oidc-provider.tsx)) is DYNAMICALLY imported by [src/main.tsx](../../src/main.tsx) ONLY when the active connection is OIDC (`resolveOidcProviderConfig()` returns non-null) — so Basic/Bearer users never load it (the tree-shake intent). `<AuthProvider>` is configured at root render from the active OIDC connection (`key` forces remount on issuer/clientId change; `onSigninCallback` cleans the `?code=&state=` URL; PKCE is default for `response_type:"code"`). Because the provider is render-time, switching INTO/OUT-OF OIDC at runtime triggers a guarded `window.location.reload()` (`reloadIfOidcProviderMismatch()` — no-op at app mount; the deliberate scope boundary, a fully-dynamic swap is deferred). Sign-in/out affordances (`oidc-sign-in` / `oidc-sign-out` / `oidc-signed-in-as`) live inline in `<ManageConnectionsPanel>` (Connection tab), reading the accessor + re-rendering on `OIDC_AUTH_CHANGED`. The `DormantAuthStrategy` placeholder (28.2) was removed once all three concretes landed; the dormancy note is gone entirely.

## Operator-feel UI labels can diverge from wire-level action verbs

**Operator-feel UI labels can diverge from wire-level action verbs (Story 12.2).** When the operator's mental model doesn't match the engine's storage model, surface the operator-feel name in the UI (handler label, button text) and the wire-level verb in the `src/api.ts` wrapper — with a docstring naming the gap. Example: "Execute now" on timer-job rows dispatches `{action: "move"}` to `/management/timer-jobs/{id}` — Flowable's terminology — because the engine "fires a timer" by moving it from the timer-jobs queue to the executable-jobs queue. Future label/verb divergences (Epic 21 task-properties, Epic 28 OIDC sign-in flows) follow the same shape: operator-feel label up top, wire-level verb in the wrapper, comment block naming the divergence. See [src/api.ts](../../src/api.ts) `executeTimerJob` and its preceding comment block.

## Event-driven API log (the Inspector drawer)

Every `request()` call pushes an entry into the in-memory `API_LOG` array (capped at 60) and dispatches a `window` `CustomEvent('api:log', { detail: entry })`. The [ApiInspector](../../src/components.tsx) component listens for this event to render real-time call history. Do **not** bypass `request()` for fetches — the Inspector will go blind.

The `ApiLogEntry` shape is `{ id, method, path, url, status, ms, at, headers?, body?, error? }`. Two NFR-8 guarantees about `headers`: the `Authorization` value is redacted **scheme-preservingly** — `Basic <base64>` becomes `Basic ***`, future `Bearer <jwt>` becomes `Bearer ***` (a value with no space falls through to `***` alone) — before the entry is pushed; the headers object handed to `fetch()` is **never** mutated (the redactor clones via spread). The optional `body` field carries the original JS value of `opts.body` for JSON requests — not the stringified form — so the drawer can pretty-print structured payloads. Response bodies are intentionally **not** captured (memory: 60 × 4 KB would balloon the buffer). Multipart `uploadDeployment()` calls log only the Authorization header, never the file contents or `FormData` parts.

**Body byte-budget in the API funnel (Story 10.2).** Request bodies passed to `request()` are funneled through `captureBody(body)` ([src/api.ts](../../src/api.ts)). Bodies whose stringified form is ≤ `BODY_BYTE_BUDGET` (16 KB) are captured by reference; larger bodies are captured as `{ __preview: <first 16 KB>, __truncated: <total bytes> }`. The ring buffer stays bounded regardless of payload size. Future bulk-input flows (variable edit, batch operations) inherit this without re-decision. `captureBody` also catches `JSON.stringify` throws (BigInt / circular refs / throwing `toJSON`, per RC-7) and falls through to the envelope shape rather than crashing the funnel.

`ErrorBox` is the canonical producer of the `app:open-inspector` event (Story 8.2): every rendered error box ships a `[data-testid="open-inspector"]` button that dispatches the event with `detail: { focusEntryId? }`, where the id is matched against `API_LOG[].error` to scroll the drawer to the offending call. The drawer's "Recent calls" tab filters by method + status bucket, expands rows on click to reveal full URL + redacted headers + request body, and applies a transient `[data-focused="1"]` highlight to the scroll target. "Copy as curl" puts real creds in the clipboard by design — NFR-8 only governs `API_LOG`; clipboard access is gated by explicit user intent (Story 8.3).

## Connection config

Persisted in `localStorage` under `flowatch.connections.v1` (Story 23.1) as `SavedConnectionsState` — `{ schemaVersion: 2, activeId, connections[] }`. The seeded default connection uses `baseUrl: http://localhost:8080/flowable-rest/service`, `username: rest-admin`, `password: test`. **New connections should use the deployment-root model: `baseUrl = http://localhost:8080` (bare host) + `servicePath = /flowable-rest/service` (per-connection override); `connectionRoot()` strips `servicePath` from `baseUrl` to recover the root, so both formats round-trip correctly.** `api.ts` is purely in-memory; mutated via `addConnection` / `updateConnection` / `deleteConnection` / `setActiveConnection` wrappers in [src/lib/saved-connections.ts](../../src/lib/saved-connections.ts). The legacy single-config key `flowatch.connection.v1` was removed in Story 23.1 — pre-23.1 settings are not migrated. Active connection surfaced via the `SettingsModal` → Connection tab (`<ManageConnectionsPanel>`).

## Vite → Flowable (native CORS) proxy chain

**Convention change — Story 34.2 (2026-06-17):** The nginx CORS sidecar (`nginx` service + `docker/nginx.conf.template` + `docker/40-validate-origin.sh`) was removed. `flowable-rest:7.2.0` now publishes host `:8080` directly with native CORS configured via Spring Boot env vars. The `docker/` directory retains only `nginx-spa.conf.template` (the published SPA image's internal web server config — unrelated to CORS).

[vite.config.ts](../../vite.config.ts) proxies `/flowable-rest` → `http://localhost:8080` (same-origin pass-through for the Vite dev server — unchanged; the dev proxy is orthogonal to native CORS). In the Docker stack, `:8080` is now `flowable` directly. The allowed CORS origin is parameterized via the `ALLOWED_ORIGIN` env var (default `http://localhost:5173`), which feeds `FLOWABLE_REST_APP_CORS_ALLOWEDORIGINS`. Spring relaxed-binding spelling (verified live against `flowable-rest:7.2.0`): hyphens within a property-name segment collapse (`allowed-origins` → `ALLOWEDORIGINS`; `allow-credentials` → `ALLOWCREDENTIALS`). The full working env-var set is in [docker-compose.yml](../../docker-compose.yml) `flowable.environment` and in [docs/compat.md](../compat.md). **No fail-fast on a malformed `ALLOWED_ORIGIN`** — Flowable emits a bad header silently; the operator is responsible (see [docs/deployment-guide.md](../deployment-guide.md)).

`bpmn-js` and `dmn-js` are pre-bundled via `optimizeDeps` and split into their own chunks (`bpmn`, `dmn`, `react`) by `manualChunks`.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Flowatch is a single-page React + Vite GUI for **Flowable 7 OSS** (BPMN/DMN process engine). It wraps the Flowable REST API and embeds the official `bpmn-js` / `dmn-js` modelers. **The app talks only to the live engine** — there is no mock fallback. If the engine is unreachable, screens show error states.

## Architecture

### Routing layer (no router library)

[src/app.jsx](src/app.jsx) holds a single `view` state string and renders one screen via a `switch` statement. There is no React Router — adding/renaming a screen means updating three places in [app.jsx](src/app.jsx): the `switch`, `VIEW_TITLE`, and `ENDPOINT_BY_VIEW` (the latter feeds the [ApiInspector](src/components.jsx) chips for that screen).

Empty-state copy for list screens lives in [src/lib/empty-states.tsx](src/lib/empty-states.tsx) — bootstrap-and-extend: every list-screen story (Deployments first, then Process Definitions, Instances, Tasks, Jobs, History, Identity) appends its own entry to the `emptyStates` record.

### API layer — single request() funnel

[src/api.js](src/api.js) is a thin wrapper around `fetch()`. Every endpoint method goes through a single `request(method, path, { params, body, base, raw, asResponse })` function that injects Basic auth, logs the call, and parses the response. Errors propagate to the caller — there is no offline fallback. `{ asResponse: true }` short-circuits the parse step and returns the raw `Response` so binary callers (e.g. `api.getDeploymentResource`) can pick `.blob()` / `.arrayBuffer()`; mutually exclusive with `raw`.

Two important details:

- **DMN lives at a different URL prefix.** Flowable's BPMN/runtime/identity endpoints are under `/flowable-rest/service`, but DMN sits at `/flowable-rest/dmn-api`. The `dmnBase()` helper rewrites the configured base URL by replacing `/service` with `/dmn-api`. Pass `{ base: dmnBase() }` for any DMN call.
- **`/identity/tenants` does not exist in flowable-rest 7.2.** `api.listTenants()` derives distinct tenant IDs from `/repository/deployments` instead.
- **Flowable job IDs are scoped to per-type namespaces** (Story 12.2). Executable jobs, timer jobs, and dead-letter jobs live in three SEPARATE URL namespaces with different valid action verbs and different stacktrace endpoints. `POST /management/jobs/{timerId}` returns 404; the `/management/timer-jobs/{id}` endpoint accepts `{action: "move"}` (fire-now) and `{action: "reschedule", dueDate: <iso>}`; `/management/deadletter-jobs/{id}` accepts `{action: "move"}`. Use the namespace-specific wrappers in [src/api.ts](src/api.ts) (`executeJob` / `executeTimerJob` / `rescheduleTimerJob` / `moveDeadLetterJob` plus three stacktrace variants). Full quirk listed as RC-11 in [docs/runtime-caveats.md](docs/runtime-caveats.md). The handler-side pattern is **tab-aware action-verb dispatch** (see below).

When adding a new endpoint, just add a wrapper in [api.js](src/api.js) and export it from the `api` object at the bottom of the file.

**Pluggable AuthStrategy seam (Story 28.1).** `request()` and `multipartFetch()` no longer hard-code Basic auth — both `await authStrategy.authorizationHeader()` (the strategy is the SINGLE header source for the funnel) and the 401 path calls `authStrategy.onUnauthorized?.()` (additive to the error — recovery side-channel, never swallows). The `AuthStrategy` interface (`kind` / `authorizationHeader(): Promise<string | null>` / optional `onUnauthorized()`) + the concrete classes live in [src/lib/auth-strategy.ts](src/lib/auth-strategy.ts) — NEW auth methods add a strategy class + a dispatcher entry; they NEVER re-edit the funnel. `BasicAuthStrategy` is the module default (reads `cfg.{username,password}` via a getter closure so `api.setConfig` / connection switches reflect without re-installing). `authorizationHeader()` is async BY DESIGN for OIDC's on-demand token refresh (Story 28.4 payoff); the `| null` return widens ADR-009's `Promise<string>` for the reserved no-auth / empty-token case (`null` → no `Authorization` header) — don't "fix" it back. The active strategy stays `BasicAuthStrategy` for the whole session until Story 28.2's `installStrategyForActiveConnection()` dispatcher swaps it per the active connection's `authStrategyConfig.kind`. Swap point: `api.setAuthStrategy(...)` / `api.getAuthStrategy()`. NFR-8 redaction is scheme-preserving (`Basic ***` / `Bearer ***`) and untouched. This is a genuine new architectural convention (not an N=k codification) — `AuthStrategy` family is N=1 concrete (Basic) at Story 28.1; Bearer (28.3) → N=2, OIDC (28.4) → N=3. **Bearer (Story 28.3, N=2):** `BearerAuthStrategy` produces `Bearer <token>` from the active connection's `authStrategyConfig.config.token` (live getter — re-paste without re-install; opaque token, NO `exp`/refresh — that's OIDC's job); empty token → `null` → no header → 401. It is the FIRST real `onUnauthorized` consumer — a 401 dispatches `OPEN_SETTINGS_AUTH` ([src/lib/nav-events.ts](src/lib/nav-events.ts)) via an injected callback, and the app listener opens `<SettingsModal>` at the Authentication tab (`initialTab` prop) so the operator re-pastes (additive to the error — the screen still shows its ErrorBox). The dormancy note narrowed to OIDC-only (Bearer is now live). **OIDC (Story 28.4, N=3 — the last placeholder swap):** `OidcAuthStrategy.authorizationHeader()` is the async seam's payoff — it `await`s an INJECTED bridge accessor's `getToken()` (in-memory access token; `automaticSilentRenew` keeps it fresh) and returns `Bearer <access-token>` or `null`. The accessor is published by `OidcTokenBridge` (`useAuth()`) into the plain-TS singleton in [src/lib/oidc-accessor.ts](src/lib/oidc-accessor.ts); the strategy reads it via the injected getter so [src/lib/auth-strategy.ts](src/lib/auth-strategy.ts) stays React-free. **`onUnauthorized()` does a DEBOUNCED (≤1 / 10 s) best-effort SILENT renew — it MUST NOT interactive-redirect (RC-18):** a Basic-only Flowable engine 401s every OIDC call, so `signinRedirect()` from the funnel would create an infinite redirect loop (call → 401 → redirect to IdP → back → 401 → …). Interactive sign-in is USER-initiated via the Auth-tab button only. **The active strategy is installed at MODULE LOAD ([src/main.tsx](src/main.tsx) calls `installStrategyForActiveConnection()` before render)** — otherwise the earliest probe / nav-count calls fire under the module-default `BasicAuthStrategy` with empty creds (`Authorization: Basic Og==`) before app.tsx's mount effect swaps it. **NFR-11:** oidc-client-ts' DEFAULT `userStore` is `window.sessionStorage` (NOT in-memory!), so the provider passes an explicit `userStore: new WebStorageStateStore({ store: new InMemoryWebStorage() })` to keep tokens in the JS heap; the `stateStore` is LEFT as the default `localStorage` (the transient PKCE `code_verifier` MUST survive the redirect round-trip). Only `{issuer, clientId, scopes}` config persists (via Story 23.2). `getToken()` must NOT call `signinSilent()` per-request (it runs on every `api.*` call — would storm the IdP with iframes). `react-oidc-context` + `oidc-client-ts` are installed; the OIDC bundle is its own Vite `manualChunks` chunk + the provider ([src/lib/oidc-provider.tsx](src/lib/oidc-provider.tsx)) is DYNAMICALLY imported by [src/main.tsx](src/main.tsx) ONLY when the active connection is OIDC (`resolveOidcProviderConfig()` returns non-null) — so Basic/Bearer users never load it (the tree-shake intent). `<AuthProvider>` is configured at root render from the active OIDC connection (`key` forces remount on issuer/clientId change; `onSigninCallback` cleans the `?code=&state=` URL; PKCE is default for `response_type:"code"`). Because the provider is render-time, switching INTO/OUT-OF OIDC at runtime triggers a guarded `window.location.reload()` (`reloadIfOidcProviderMismatch()` — no-op at app mount; the deliberate scope boundary, a fully-dynamic swap is deferred). Sign-in/out affordances (`oidc-sign-in` / `oidc-sign-out` / `oidc-signed-in-as`) live in the Auth tab, reading the accessor + re-rendering on `OIDC_AUTH_CHANGED`. The `DormantAuthStrategy` placeholder (28.2) was removed once all three concretes landed; the dormancy note is gone entirely.

**Operator-feel UI labels can diverge from wire-level action verbs (Story 12.2).** When the operator's mental model doesn't match the engine's storage model, surface the operator-feel name in the UI (handler label, button text) and the wire-level verb in the `src/api.ts` wrapper — with a docstring naming the gap. Example: "Execute now" on timer-job rows dispatches `{action: "move"}` to `/management/timer-jobs/{id}` — Flowable's terminology — because the engine "fires a timer" by moving it from the timer-jobs queue to the executable-jobs queue. Future label/verb divergences (Epic 21 task-properties, Epic 28 OIDC sign-in flows) follow the same shape: operator-feel label up top, wire-level verb in the wrapper, comment block naming the divergence. See [src/api.ts](src/api.ts) `executeTimerJob` and its preceding comment block.

### Event-driven API log (the Inspector drawer)

Every `request()` call pushes an entry into the in-memory `API_LOG` array (capped at 60) and dispatches a `window` `CustomEvent('api:log', { detail: entry })`. The [ApiInspector](src/components.tsx) component listens for this event to render real-time call history. Do **not** bypass `request()` for fetches — the Inspector will go blind.

The `ApiLogEntry` shape is `{ id, method, path, url, status, ms, at, headers?, body?, error? }`. Two NFR-8 guarantees about `headers`: the `Authorization` value is redacted **scheme-preservingly** — `Basic <base64>` becomes `Basic ***`, future `Bearer <jwt>` becomes `Bearer ***` (a value with no space falls through to `***` alone) — before the entry is pushed; the headers object handed to `fetch()` is **never** mutated (the redactor clones via spread). The optional `body` field carries the original JS value of `opts.body` for JSON requests — not the stringified form — so the drawer can pretty-print structured payloads. Response bodies are intentionally **not** captured (memory: 60 × 4 KB would balloon the buffer). Multipart `uploadDeployment()` calls log only the Authorization header, never the file contents or `FormData` parts.

**Body byte-budget in the API funnel (Story 10.2).** Request bodies passed to `request()` are funneled through `captureBody(body)` ([src/api.ts](src/api.ts)). Bodies whose stringified form is ≤ `BODY_BYTE_BUDGET` (16 KB) are captured by reference; larger bodies are captured as `{ __preview: <first 16 KB>, __truncated: <total bytes> }`. The ring buffer stays bounded regardless of payload size. Future bulk-input flows (variable edit, batch operations) inherit this without re-decision. `captureBody` also catches `JSON.stringify` throws (BigInt / circular refs / throwing `toJSON`, per RC-7) and falls through to the envelope shape rather than crashing the funnel.

`ErrorBox` is the canonical producer of the `app:open-inspector` event (Story 8.2): every rendered error box ships a `[data-testid="open-inspector"]` button that dispatches the event with `detail: { focusEntryId? }`, where the id is matched against `API_LOG[].error` to scroll the drawer to the offending call. The drawer's "Recent calls" tab filters by method + status bucket, expands rows on click to reveal full URL + redacted headers + request body, and applies a transient `[data-focused="1"]` highlight to the scroll target. "Copy as curl" puts real creds in the clipboard by design — NFR-8 only governs `API_LOG`; clipboard access is gated by explicit user intent (Story 8.3).

### Connection config

Persisted in `localStorage` under `flowatch.connection.v1` (`baseUrl`, `username`, `password`, `tenantId`). Defaults: `http://localhost:8080/flowable-rest/service`, `rest-admin`/`test`. Mutated via `api.setConfig(...)` or the `SettingsModal` (gear icon).

### Modelers

The modeler components live in [src/modeler/](src/modeler/) as a small directory of sibling files: `BpmnModeler.tsx`, `DmnModeler.tsx` (Story 16.4), and `starters.ts` (shared starter XMLs — `BLANK_BPMN_XML`, `LOAN_BPMN_XML`, `LOAN_DMN_XML`). Both modelers wrap `bpmn-js/lib/Modeler` and `dmn-js/lib/Modeler` directly (not the React bindings). Each component instantiates the vanilla class in a `useEffect`, attaches it to a ref'd `<div>`, and bridges save actions to `api.deployBpmn` / `api.deployDmn`. CSS for the modelers is imported once in [src/main.tsx](src/main.tsx) — both `bpmn-js/dist/assets/*.css` and `dmn-js/dist/assets/*.css`.

The BPMN modeler:
- Lists deployed definitions in a dropdown and loads the raw XML via `GET /repository/process-definitions/{id}/resourcedata`.
- The embedded `LOAN_BPMN_XML` literal is the default starter when no real definition is selected; `BLANK_BPMN_XML` is loaded when the user picks "new from scratch".
- Deploys via `api.deployBpmn`, which performs a multipart `POST /repository/deployments` (Flowable rejects JSON-with-base64; the mock-mode shape from earlier no longer applies).

The DMN modeler is similar but its REST calls go to the `dmn-api` sub-app (see API layer note above).

The Upload modal at [src/lib/upload-deployment-modal.tsx](src/lib/upload-deployment-modal.tsx) (Story 9.2) is the GUI-driven counterpart to the modeler's Save-and-deploy — both routes ultimately call `api.deployBpmn(filename, xml)`.

**Pattern P-006 — Vanilla bpmn-js / dmn-js wrapping (Story 16.1).** The modelers are wrapped via direct vanilla-class instantiation, NOT via the `bpmn-js-react` (or `dmn-js-react`) bindings (per ADR-001). The pattern:

1. The vanilla `Modeler` class is instantiated inside a `useEffect` and attached to a ref'd `<div>` (`containerRef`).
2. Event-bus subscriptions (`selection.changed`, `commandStack.changed`, `element.dblclick`, `views.changed`, etc.) are typed via `diagram-js`'s `EventBus<EventMap>` — with **local payload interfaces** naming the actually-observed fields, since diagram-js doesn't publish BPMN/DMN-specific event payloads. The local interface lives alongside the modeler component (see `SelectionChangedEvent` + `CommandStackChangedEvent` in [src/modeler/BpmnModeler.tsx](src/modeler/BpmnModeler.tsx)).
3. The cleanup function unsubscribes ALL handlers + calls `modeler.destroy()` to release WebGL / canvas resources. Wrap the `destroy()` call in try/catch — bpmn-js can throw on already-disposed modelers when React strict-mode double-mounts.
4. CSS for the modeler is imported once in `src/main.tsx` (NOT per-component) — both `bpmn-js/dist/assets/*.css` and `dmn-js/dist/assets/*.css` load at module init.
5. The modeler chrome (toolbar + dropdown + deploy button row) honors `data-density` via CSS variables — `var(--row-h)`, `var(--pad)`, `var(--gap)` — so toggling density in TweaksPanel rescales the chrome WITHOUT remounting the canvas (UX Q-5). Hardcoded pixel values inside `.mod-toolbar` and its children are no longer permitted.
6. Shared starter XMLs live in [src/modeler/starters.ts](src/modeler/starters.ts) as named exports — not embedded literals inside the modeler component. `BLANK_BPMN_XML` is the "New from scratch" template; `LOAN_BPMN_XML` and `LOAN_DMN_XML` are the demo defaults loaded when no real definition / decision is selected.

See [src/modeler/BpmnModeler.tsx](src/modeler/BpmnModeler.tsx) for the BPMN reference implementation and [src/modeler/DmnModeler.tsx](src/modeler/DmnModeler.tsx) (Story 16.4) for the DMN counterpart. The pattern is preserved verbatim through the TypeScript migration (ADR-001) — no shift to React bindings is justifiable for v0.0.2.

**Pattern P-006 consumer N=3 — `@bpmn-io/form-js-viewer` task forms (Story 29.1, FR-23).** The form-js viewer is the 3rd P-006 consumer (after bpmn-js / dmn-js). It wraps the vanilla `Form` class from `@bpmn-io/form-js-viewer` EXACTLY like the modelers: instantiated in a `useEffect` on a ref'd `<div>` (`.form-js-host`), loaded via `form.importSchema(schema, data)` (returns a promise — a malformed schema rejects → in-panel `ErrorBox`, never a blank panel), submit bridged via `form.on("submit", handler)` typed with a LOCAL `FormJsSubmitEvent` interface (`{ data, errors }` — form-js publishes no React-typed payload), cleanup `form.off(...)` + `form.destroy()` in try/catch. CSS imported ONCE in [src/main.tsx](src/main.tsx) (`@bpmn-io/form-js-viewer/dist/assets/form-js-base.css` + `form-js.css`); the form-js bundle is its own `forms` Vite `manualChunks` chunk mirroring `bpmn`/`dmn`/`oidc`. Native form-js styling is overridden by Flowatch's `data-look` tokens via `.form-js-host .fjs-container` remapping form-js's own `--color-*` vars to `--fg`/`--bg`/`--accent`/`--line` in [src/styles/components.css](src/styles/components.css) (Pattern P-007 — no hard-coded colors). The render branch lives INSIDE the existing `<TaskFormPanel>` (Story 11.3, 2nd panel-as-sibling consumer — NOT a new sibling/extraction). `classifyTaskForm(payload)` ([src/components/TaskFormPanel.tsx](src/components/TaskFormPanel.tsx)) discriminates: a NON-EMPTY `components` array → form-js, a NON-EMPTY `formProperties` array → legacy (Story 11.3 renderer kept VERBATIM as the FR-23 fallback), else → "none" empty state. **The length check is load-bearing** — flowable-rest:7.2.0 returns `{ formKey: null, formProperties: [] }` (present-but-empty) for no-form tasks, so a bare `Array.isArray` check wrongly classifies no-form tasks as `legacy` and hides the Complete button (golden-path regression). Both branches submit wire-identically through `api.submitTaskForm` (`/form/form-data`, FR-22) — the form-js `data` object maps to the SAME `{ properties: [{ id, value }] }` envelope via `mapFormJsData` (`Object.entries(data).map(([id, value]) => ({ id, value: String(value) }))`); NO new endpoint. **COMPAT BOUNDARY:** the default image has no REST path that returns a `components` array (`/form-api/*` is 404, compat.md), so the form-js branch is **fixture-verified** (unit + a `page.route`-injected e2e fixture in [e2e/task-form-js-render.spec.ts](e2e/task-form-js-render.spec.ts)) and DORMANT against `make stack` by design — a live form-js render needs an alternate image or a future embedded-form read path (deferred-work). **Flowable BPMN properties panel — moddle descriptor + element-type field dispatch (Story 30.1, FR-38 / D-8 / ADR-006).** The BPMN modeler's `.mod-props` panel exposes Flowable element extensions as editable fields backed by a registered moddle descriptor. Each field carries `data-testid="bpmn-prop-<attr>"` + a `mono` wire-attribute label (operator-feel label up top, wire attr in `<span className="mono">`). The listener / field-injection / in-out editors are reusable presentational sub-components (`<ListenerEditor>` etc.) — the field-cluster widget, NOT the kind dispatch. Story 30.1 removed the `bpmn-properties-pending-banner` placeholder (placeholder-then-real). `bpmn-moddle` has no published types — [src/modeler/bpmn-moddle.d.ts](src/modeler/bpmn-moddle.d.ts) is a minimal ambient shim (ADR-001 `any` zone). Asserts XML OUTPUT not CSS-class-on-SVG, so the Epic 26 AI-2 computed-style canvas discipline is N/A (noted in the e2e). **There is intentionally NO DMN moddle descriptor (Story 30.2): Flowable's DMN converter consumes standard OMG DMN — it ships zero `flowable:`-namespace extensions; inventing one would type nothing real and risk round-trip corruption.**

**DMN properties surface — no Flowable extensions, standard-metadata + JUEL discipline (Story 30.2, ADR-006 DMN half).** Documented negative finding (AC-1): the Flowable DMN XML converter consumes **standard OMG DMN** — its parser schema directory ([flowable-dmn-xml-converter/.../parser](https://github.com/flowable/flowable-engine/tree/main/modules/flowable-dmn-xml-converter/src/main/resources/org/flowable/impl/dmn/parser)) contains only `DC.xsd` / `DI.xsd` / `DMN12.xsd` / `DMN13.xsd` / `DMNDI12.xsd` / `DMNDI13.xsd` / `dmn.xsd` (all targeting `http://www.omg.org/spec/DMN/20151101`); there is **no** Flowable-specific DMN namespace analogous to BPMN's `http://flowable.org/bpmn`. A Pattern P-008 guard in `dmn-roundtrip.test.ts` parses [DmnModeler.tsx](src/modeler/DmnModeler.tsx) and asserts no `FEEL` literal is introduced (excluding the project's "operator-feel" UX term), protecting RC-13 against a future "fix FEEL labeling" regression.

### Modal conventions

**Modal focus-restore via `triggerRef` (Story 10.2).** Modals accept `triggerRef?: React.RefObject<HTMLElement | null>` and call `triggerRef.current?.focus()` on Esc / Cancel / successful submit. Callers pass `useRef` on the trigger button (the menuitem or the explicit Open button); a single `triggerRef` per surface is enough since only one modal can be open at a time. All current modals — [upload-deployment-modal.tsx](src/lib/upload-deployment-modal.tsx), [delete-deployment-modal.tsx](src/lib/delete-deployment-modal.tsx), [start-instance-modal.tsx](src/lib/start-instance-modal.tsx), [cancel-instance-modal.tsx](src/lib/cancel-instance-modal.tsx) — use this shape. New modals MUST as well.

**`fallbackRef` focus-restore for destructive modals whose trigger row is removed by the action (Story 19.2 codification, N=4 cross-domain at Epic 23 close).** Destructive modals whose trigger lives in a row that the action ITSELF unmounts (delete-then-reload pattern) accept `fallbackRef?: React.RefObject<HTMLElement | null>` alongside `triggerRef`. The modal's `restoreFocus()` helper checks `document.contains(triggerRef.current)` and falls back to `fallbackRef.current` when the trigger is detached; if neither is in the document, focus silently falls to `<body>` (the silent-no-op clause is what makes cross-domain transfer painless). N=4 consumers today: `<DeleteVariableModal>` (Story 19.2 — runtime variables panel anchor, `fallbackRef` = `addBtnRef`), `<DeleteUserModal>` (Story 22.2 — identity, `fallbackRef` = `backLinkRef` on the `/identity/users/$id` detail page's "← Back" link), `<DeleteGroupModal>` (Story 22.3 — identity, same `backLinkRef` shape on the group detail page), `<DeleteConnectionModal>` (Story 23.1 — saved-connections, `fallbackRef` = the Manage-connections panel's `Add connection` button — the FIRST consumer to use a panel-button fallback rather than a header / back-link fallback). The fallback-target shape varies by parent route: row-in-list-panel → panel's own primary button (Story 19.2 + Story 23.1); row-in-list-route → detail page's back-link or list header's "New X" button (Story 22.2 + Story 22.3). Per "Never extract at N=4" this paragraph IS the codification, NOT an extraction event — same shape as PUT-with-partial-fields, panel-as-sibling, tab-aware action-verb dispatch. ### Panel-as-sibling-component (Story 10.4)

Detail pages with multiple panels use sibling components rather than inline panel logic. Each panel owns its own `useApi`, its own four-state rendering, its own refresh affordance, and its own row-count badge. The parent component mounts the panel with a single stable identifier prop (e.g. `<InstanceVariablesPanel instanceId={id} />`) — no callbacks, no state-threading. See [src/components/InstanceVariablesPanel.tsx](src/components/InstanceVariablesPanel.tsx) and [src/components/TaskFormPanel.tsx](src/components/TaskFormPanel.tsx). Future multi-panel detail pages (Historic Activity Instances, task detail with form + variables + history) follow this shape.

**Parent-level state-gating fetches are an acceptable duplication, not a refactor target (Story 11.3).** When the parent needs the panel's loaded state to gate its own UI — e.g. `<TaskDetail>` hides the legacy Complete button when a form is present (Story 11.3 AC-9) — the parent runs its OWN `useApi` against the same endpoint. Both calls go through the funnel; the Inspector shows two entries. Do NOT thread the panel's internal state up via a callback prop; that breaks the single-stable-identifier contract above and tightly couples parent UI to panel internals.

**Panel-as-sibling is never extracted into a shared abstraction (Epic 12 retro R-2 decision, 2026-05-25).** Four consumers (10.4 `InstanceVariablesPanel`, 11.3 `TaskFormPanel`, 12.4 `JobStacktracePanel`, 13.2 historic-activities panel) and counting; the three-consumer extraction trigger has been deliberately resisted at each evaluation point. The pattern's value IS the conformance: each panel owns its `useApi`, its four-state contract, its refresh affordance, its row-count badge. An extracted `<PanelAsSibling>` helper would either expose diverging render shapes through props (defeating the abstraction) or constrain future panels to a shape that's wrong for them. The cost of "duplication" here is ~30 LOC per panel of obvious, locally-readable code. Future N+1 / N+2 consumers DO NOT need to re-evaluate; this is project policy.

**Time-spanning detail pages use a single route + dual fetches, not split routes (Epic 12 retro R-1 decision, 2026-05-25).** When a detail page must show both runtime and historic state for the same entity (canonical example: `/instances/:id` showing runtime status when the instance is live AND historic record when it has ended), use ONE route with sibling panels — each panel runs its own `useApi`; the runtime panel renders an empty / "instance ended" state when the runtime fetch 404s; the historic panel renders an empty / "no historic record yet" state when the historic fetch 404s. Do NOT split into `/instances/:id` and `/history/instances/:id` — the operator's mental model is "this is the instance, here's everything I know about it." See Epic 13 Story 13.1 / 13.2 acceptance criteria. The pattern reuses the panel-as-sibling shape above; the parent route stays a thin shell.

**Row-expand-for-detail (Story 15.4).** Some detail content is small enough to render inline within an expanded row of the parent table — forensic-trace context where the row's metadata AND the expanded content are operator-relevant TOGETHER (a separate detail route would split the context). The DMN executions list at `/decisions?tab=executions` is the canonical example: each row's input + output variables render inline on row-click. Rules: ONE row expands at a time (`expandedId: string | null`, not a Set — clicking another row collapses the previous); the expand-toggle is the whole row, not a separate chevron button (the chevron is decorative; the row is the click target); expanded content renders as a `colSpan`-spanning `<tr>` IMMEDIATELY BELOW the clicked row so screen-readers and keyboard navigation traverse it in order; a `data-testid="<entity>-detail-${id}"` attribute on the expansion `<tr>` is the E2E contract. Row-expand is NOT a replacement for panel-as-sibling — use row-expand when the expanded data is already loaded with the parent row; use panel-as-sibling when the expanded data requires a separate fetch. See `<DmnExecutionsList>` at [src/routes/decisions/index.tsx](src/routes/decisions/index.tsx). Future candidates: Epic 18's stacktrace-on-row-expand (job error details, if it lands a row-shape rather than the sibling panel it has today), any future historic-record-as-row-expand surface.

### Cross-story sequencing conventions

**Placeholder-then-real (multi-epic pattern).** When a story references functionality that arrives in a later story, ship a `data-testid`-anchored placeholder in the earlier story (e.g. a toast that says "X arrives in Story Y.Z"). The `data-testid` is the swap point — the downstream dev replaces the handler without changing markup. Precedents: 9.1's `data-testid="upload-deployment"` (swapped by 9.2), 9.1's two-Delete-items (collapsed by 9.3), 9.4's `Start instance` toast (swapped by 10.2), 10.1's `Cancel` toast (swapped by 10.3). **The swap PR MUST also drop the placeholder-toast E2E assertion from the earlier story's spec file in the same PR** — otherwise the earlier story's E2E asserts a toast text that no longer fires and CI red-builds until the cleanup commit lands (Epic 10 retro §3.5).

**UX-polish cadence is opt-in by next story.** Canonical archetype stories ship working `window.confirm()` / native form elements / default styles. The polish story swaps to design-system equivalents. See 9.1 (`confirm()` for delete) → 9.3 (`DeleteDeploymentModal`); `prompt()` on instance detail → 10.3 (`CancelInstanceModal`). Don't preempt polish in the archetype; don't skip polish in the polish story.

**Review-patch-fold vs post-closure-fixup decision matrix (Epic 12 retro §4.3).** Two defensible shapes for live-engine discoveries that arrive mid-epic: **(a) post-closure fixup commits** — appropriate for *genuine surprises* (engine contract mismatch, missing endpoint, undocumented behaviour); produces bisectable "what was the gap between spec'd and shipped" history; Epic 11's three fixup commits (`89de10f` / `f60756f` / `8c8bd51`) are the precedent. **(b) review-patch fold into originating commit** — appropriate for *scope expansion within original story intent* (the engine exposes additional related actions that the story's intent reasonably covers); produces "story shipped with full real action surface" history; Epic 12's `213bef0` (timer-job namespace absorption) and `eb7e377` (`RescheduleTimerModal` source absorption) are the precedent. Pick deliberately. **Review-patches that ADD files must land all-or-nothing in one commit** — splitting test and source across two commits breaks `git bisect` because the test-only commit fails to compile (Epic 12 retro §3.3).

**Bundled refactor + feature avoidance for canonical-archetype migrations (Epic 12 retro §3.4).** When a canonical-archetype rewrite removes more than 50 LOC from [src/screens.tsx](src/screens.tsx) (or any other legacy file), **split the legacy-removal into its own `chore(refactor):` commit** before the feature commit. Story 12.1 bundled a 155-LOC `<JobsScreen>` deletion into the rewrite commit (`886c76e`); the cost was one less bisectable boundary. Story 13.3 was the first deliberate application of the split (`268eee4` feat + `87b9f98` chore(refactor) — −373 LOC from `src/screens.tsx`); per-commit `npm test` was green on both, bisectability cost was zero. Future canonical-archetype migrations (Epic 14 identity, Epic 15 DMN, Epic 16 modeler rewrite) follow the two-commit shape — one extra commit per migration is the price for durable bisectability.

**`<LegacyXxxShim>` transitional-migration pattern for multi-tab screens (Epic 13 retro §4.4).** When a canonical-archetype migration of a multi-tab screen lands one tab at a time, ship a wrapper component (`<LegacyXxxShim>`) that mounts the un-migrated tabs' legacy code with a `type` prop. The migrating tabs route through the canonical archetype; non-migrated tabs route through the shim. The final migration story (or its `chore(refactor):` follow-up commit) deletes the shim alongside the legacy block. See Story 13.1 (introduced `<LegacyHistoryShim>` to keep `?type=variables|tasks|activities` rendering while `?type=instances` migrated) and Story 13.3's `87b9f98` chore(refactor) (deleted both the shim and the legacy `<History>` block). Future candidates: Epic 14 identity (users / groups), Epic 15 DMN (decisions / deployments), Epic 16 BPMN modeler rewrite. The shim is a transitional artefact, never a permanent abstraction.

**Live-engine-walkthrough commit shapes — 3-row decision matrix (Epic 13 retro §4.5).** Extends the review-patch-fold matrix above to a third category — scope expansion BEYOND original story intent — that the original two-row matrix didn't address:

| Category | Recommended commit shape |
|---|---|
| Genuine bug-fix (engine surprise; spec was reasonable) | Post-closure `fix:` commit (Epic 11 shape) OR fold into originating commit if mid-review (Epic 12 shape) |
| Scope expansion within original story intent | Fold into originating story commit (Epic 12 §4.3) — review-patches that ADD files must land all-or-nothing in one commit |
| Scope expansion BEYOND original story intent (symmetry-completeness, unanticipated engine recipe) | **Standalone post-closure `feat:` commit + DAR-Change-Log append on the most-relevant story** — gives bisectable per-feature history; story-as-shipped matches story-as-spec'd; commit body documents the expansion rationale. Epic 13's `b2713d1` (historic-variables panel mirrors runtime) and `78b323a` (runtime-activities via historic endpoint) are the precedent. |

Pick deliberately when the live-engine walkthrough surfaces output. The "DAR-Change-Log append" step matters — without it, the only forensic record for the scope expansion lives in the standalone commit body, divorced from any story file.

**Bundled mega-polish commits — splitting rule (Epic 14/15/16 retro F-2).** When a polish PR touches >5 files OR mixes >2 rows of the 3-row decision matrix above, split into per-row commits. Row 1 (genuine bug-fix) and Row 3 (scope expansion beyond intent) MUST NOT share a commit — they have different decay characteristics under `git bisect`. Epic 15's `4824aa5` (3825 insertions across 35 files; Rows 1+2+3 simultaneously: JUEL bug-fixes, wrapper realignment, DTO narrowing, UX uplift, audit enrichment, CSS fixes, E2E seeding) is the anti-pattern precedent — a future `git bisect` for "when did the typed Execute form break?" cannot isolate UX item 4 from the Row 1 bug-fixes. Split the next one even when the operator-review surface produces a temptation to ship "all the fallout at once."

**Post-smoke fixup commits MUST append to the originating story's DAR-Change-Log in the same PR (Epic 14/15/16 retro AI-3).** The Senior Developer Review (AI) block lock fires at `Status: review → done`; post-smoke fixups land *after* that gate, so the lock provides no enforcement. The discipline is operator-side: every `fix:` / `feat:` / `chore:` commit on `develop` that materially extends a closed story's shipped scope must append a row to that story's Change Log table (`Date | Story | Summary` + commit SHA in parens) before the commit lands. Epic 14/15/16 shipped 8 forensic-gap commits; AI-1 backfilled them retroactively. The next epic batch's retro will escalate to a `.claude/hooks/post-merge.sh` if this discipline isn't held by-hand.

**Sprint-status per-story flip happens ONLY at epic retro (Epic 21 retro AI-1 codification).** The dev / code-review path commits straight to develop without re-entering the `bmad-sprint-status` skill — `{N}-{M}-*` story keys flip from `ready-for-dev` / `in-progress` → `done` ONLY when `bmad-retrospective` fires its cross-file flip override at epic close. Mid-epic flip-lag (story key shows `ready-for-dev` while the commit is on develop) is the EXPECTED steady state, NOT a regression. The `_bmad/custom/bmad-sprint-status.toml` override suppresses the base-skill risk warning for this case (only `ready-for-dev` + zero matching commits + >14-day-stale last_updated still raises a real stalled-story signal). Epic 13 / 14 / 15 / 16 / 17 / 18 / 19 / 20 / 21 retros all debated automation (post-commit git hook, dev-story `on_complete` flip, Makefile sync target) and each one concluded the cost-benefit didn't justify the maintenance surface. The convention is silence + epic-close batch flip. Operators reading sprint-status see real story counts; the `bmad-retrospective.toml` override handles the flip at the right cadence. If a future epic-batch produces enough stories that the retro flip becomes unwieldy (canonical threshold: >10 stories per epic), revisit this lock and consider automation per the Epic 21 retro AI-1 question matrix.

**DAR-block discipline is enforced at the bmad-sync chokepoint (Epic 18 retro AI-1).** The Epic 13 retro A-3 (option b) populated-content lock in `_bmad/custom/bmad-dev-story.toml` is **skill-scoped** — it fires inside the `bmad-dev-story` skill flow. Direct-commit paths bypass the skill entirely; Epic 18 shipped 4 stories with empty Dev Agent Record / Senior Developer Review (AI) blocks because the dev path never routed through the lock (Epic 18 retro §3.1 / F-3). The git-scoped complement is [scripts/ci/check-dar-blocks.sh](scripts/ci/check-dar-blocks.sh), invoked from [scripts/bmad-sync.sh](scripts/bmad-sync.sh) (the single chokepoint for private-repo commits). It refuses to commit any story file whose `Status:` is `review` or `done` while these placeholder strings remain: `(Populated by the dev agent during implementation.)`, `_To be populated by the reviewer after implementation._`, `_To be populated by dev agent._`. The structural guard is `## Dev Agent Record` heading presence — retros, sprint-status, deferred-work, spec-*, milestone-* don't carry it and are auto-skipped. Run `make check-dar` for an ad-hoc audit. Residual gap: a maintainer typing `git -C <private-repo> commit` by hand still bypasses the hook; documented as accepted (the alternative — a private-repo-side `.git/hooks/pre-commit` — would diverge from the project's `scripts/ci/*.sh` discipline and would need bootstrap wiring in `setup-bmad.sh`).

**Bake-commit-after-retro discipline — calibrated by batch size (Epic 18 retro AI-2).** When a retrospective's action items include CLAUDE.md updates, the bake-commit promise (`chore(docs): bake Epic N retro outputs for Epic N+1`) is **calibrated by batch size, not blanket-applied**: (a) **batches with ≤2 distinct CLAUDE.md concerns** may fold those paragraphs into the next feat commit that exercises the pattern — Pattern P-008's landing inside Story 18.2's `525a8a9` is the precedent; (b) **batches with >2 distinct CLAUDE.md concerns** (e.g. Epic 14/15/16 retro had AI-1 backfill 8 DAR rows + AI-2 splitting rule + AI-3 post-smoke append) keep the `chore(docs):` bake-commit shape so `git bisect "when did concept X get documented?"` lands on a docs commit, not a conflated feat commit. The Epic 17 retro promised a bake commit for a 1-paragraph batch (P-008) and silently folded it — functionally equivalent, structurally inconsistent (Epic 18 retro §3.3 / D-4). Next-retro authors: count the CLAUDE.md concerns in your AI list BEFORE writing the bake-commit promise.

**Spec-authoring discipline: grep-verify every "reused from X" claim (Epic 13 retro §3.3).** When a story's Dev Notes asserts that a helper / component / DTO is "reused verbatim from [src/file.tsx]" or "extracted from [src/file.tsx]", the spec author MUST grep the named file at spec-authoring time to confirm the symbol actually lives there. Story 13.1's spec claimed `fmtMs` was already exported from `src/components.tsx`; the dev discovered it was local to `src/screens.tsx` and had to add the export as a scope-creep task. Lightweight (one extra `grep` per "reused from" claim); prevents the dev from inheriting an inaccurate spec. Apply to every future spec.

**Spec-symmetry discipline: every runtime/historic, claim/unclaim, start/cancel, add/remove story author runs a symmetry-completeness check (Epic 13 retro §3.2 + §3.7).** When a story touches one half of a paired action surface (runtime variables ↔ historic variables; claim ↔ unclaim; start ↔ cancel; add user to group ↔ remove user from group), the spec author runs an explicit symmetry-completeness check: does the spec address both halves? If not, name the gap in the spec (intentional deferral) or expand scope to cover the symmetric pair. Story 13.1's `<InstanceRuntimePanel>` shipped with nested variables but `<InstanceHistoricPanel>` did NOT until post-closure `b2713d1` — the asymmetry was predictable at spec authoring; the live-engine walkthrough caught what spec review didn't. Future Epic 14 (add/remove user from group), Epic 19 (edit/delete variable), Epic 21 (add/delete attachment), Epic 22 (create/update/delete user) and Epic 25 (BAR upload/delete) all touch symmetric action pairs — flag the symmetry check as an explicit spec-authoring task.

**Discipline-lock authoring: gate on populated content, not block presence (Epic 13 retro §4.6).** When a `_bmad/custom/<skill>.toml` discipline lock is added to enforce "the dev MUST produce artefact X before flipping status," the lock condition MUST be populated-content gating, not string-presence gating. Locks that only check "does the section header exist" are easy to satisfy with placeholder content (`_To be populated…_`). ### Cross-component state patterns

**Map-symmetry for reverse-action pairs (Epic 11 retro §4.2).** When a story adds the inverse of an existing optimistic-UI action (e.g., unclaim alongside claim, reopen alongside resolve, unassign alongside assign), reuse the existing `Map<string, V>` with a distinct sentinel value (`""` for "intentionally empty"; `null` for "engine-state restored"). Do NOT introduce twin Maps. See [src/routes/tasks/index.tsx](src/routes/tasks/index.tsx) where `optimisticClaimed: Map<string, string>` is consumed by both `handleClaim` (sentinel = username) and `handleUnclaim` (sentinel = `""`); the reconciliation `effectiveAssignee = optimisticClaimed.get(t.id) ?? t.assignee ?? ""` handles both "just claimed" and "just unclaimed" cleanly.

**Sequence-counter race guard (Epic 11 retro §4.5).** When concurrent listener firings can each launch an async fetch and only the latest result should commit, use a `useRef(0)` sequence counter — increment on entry, snapshot the value, only `setState` if the snapshot matches the current sequence:

```ts
const seq = useRef(0);
const refresh = useCallback(async () => {
  const mySeq = ++seq.current;
  const counts = await fetchCounts();
  if (mySeq === seq.current) setCounts(counts);  // only latest wins
}, [tenant.id]);
```

Strictly stronger than an in-flight ref guard (which drops mutations) and trivially simpler than `AbortController` for read-only data. See [src/app.tsx](src/app.tsx)'s `refreshNavCounts`. Reusable for search-as-you-type filtering, dashboard tile refresh on tenant switch, or any future autosave-with-conflict-resolution scenario.

**Tab-aware action-verb dispatch (Epic 12 retro §4.2).** When a URL search-param drives both the list endpoint AND the action verbs that apply to rows, dispatch in the handler — not in a separate handler-per-tab. The discriminant stays in scope at the row action; the handler reads as plain `if (type === "X") await api.tabXAction(j.id); else await api.defaultAction(j.id);`. See `handleExecute` in [src/routes/jobs/index.tsx](src/routes/jobs/index.tsx) branching between `api.executeJob` and `api.executeTimerJob` based on the `type` search-param, and `loadIdentity` in [src/routes/identity/index.tsx](src/routes/identity/index.tsx) branching between `api.listUsers` and `api.listGroups` on the `tab` search-param.

**Never extract at N=4 (Epic 14 retro precedent codification, 2026-05-26).** The pattern reached N=4 consumers in Story 14.2's `loadIdentity` branch (Execute / Move / history-tab read / identity-tab read). The N=3 extraction trigger was deliberately resisted; the N=4 codification mirrors R-2 (never extract panel-as-sibling). Inline 2-LOC dispatch beats any 8-LOC `useTabbedLoader` hook on every dimension: locally readable; the discriminant stays at the call site; future tab additions don't have to learn the hook. Future N+1 / N+2 consumers DO NOT need to re-evaluate; this is project policy.

**PUT-with-partial-fields wrapper family (Epic 22 retro N=4 codification).** When the engine exposes a PUT endpoint that accepts a `Partial<…>` body of editable fields on a single entity — Story 20.1 `updateProcessDefinition(id, {category})`, Story 21.1 `updateTask(id, {priority, dueDate, owner, assignee})`, Story 22.2 `updateUser(id, {firstName, lastName, email, password})`, Story 22.3 `updateGroup(id, {name, type})` — the canonical wrapper shape is `(id: string, fields: Partial<EditableFields>) => Promise<Entity>` funneling through `request<Entity>("PUT", "/path/{id}", { body: fields })`, throwing `Error("<name> requires at least one field")` on empty `fields`. The four wrappers are intentionally inline clones — NOT extracted into a shared helper. The cost of "duplication" is ~5 LOC per wrapper of obvious, locally-readable code; an extracted `createPartialPutWrapper<T>(path, name)` helper would either expose diverging shapes through generic constraints (defeating the abstraction) or constrain future PUT wrappers to a shape that's wrong for them (e.g., when the engine wants a wrapper field like `body: { variables: [...] }` instead of `body: fields`, or when only some endpoints take `encodeURIComponent` on the id segment). Future N+1 / N+2 consumers DO NOT need to re-evaluate; this is project policy. Operator-feel-distinct PUT wrappers (where the same wire URL hosts multiple wrappers per CLAUDE.md "Operator-feel UI labels can diverge from wire-level action verbs") MUST each get their own wrapper with their own JSDoc — `suspendProcessDefinition` + `updateProcessDefinition` co-exist on the same URL even though both are PUTs because their operator-feel diverges. The companion modal-archetype shape is retryable-creation with diff-empty no-op guard (Story 21.1 AC-8 codification, reapplied in `<EditUserModal>` Story 22.2 + `<EditGroupModal>` Story 22.3). Forward-reference candidates: Story 23.1 saved-connections edit, Story 28 OIDC client edit. The "Never extract at N=4" reverse-logic rule fires here alongside its sibling codifications: panel-as-sibling (Epic 12 retro R-2), tab-aware action-verb dispatch (Epic 14 retro), and Pattern P-008 token-contract guard tests (Story 18.4).

**Cross-component invalidation events live in `src/lib/nav-events.ts` (Epic 11 retro A-2).** The `NAV_INVALIDATE_COUNTS` constant is dispatched after mutations that change Sidebar badge counts (Claim / Complete / Delegate / Unclaim / Execute / Move / Start / Cancel / Resolve / form submit). The app-level listener in [src/app.tsx](src/app.tsx) refetches counts; the sequence-counter race guard above keeps it safe under concurrent dispatch. Add new `nav:*` events as named exports in the same module; never use bare string literals in dispatch sites (a `grep '"nav:invalidate-counts"' src/` regression-guard exists).

### State / data fetching pattern

Screens use a small `useApi(fn, deps)` hook in [src/screens.jsx](src/screens.jsx) that returns `{ loading, data, error, reload }`. Every screen renders three states: loading, error (with the actual error message — no silent fallbacks), and empty (`No records.`). When you add a screen, follow this pattern rather than introducing a state library.

**v1 canonical for list screens (Story 9.1 onwards):** URL-identity list data uses TanStack Router's `loader` + `pendingComponent` + `errorComponent` slots (precedent: [src/routes/deployments/index.tsx](src/routes/deployments/index.tsx)). `useApi` remains the pattern for secondary fetches inside components. The migration of the other list screens (Process Definitions, Instances, Tasks, Jobs, History, Identity) lands in subsequent Epic 9-15 stories — until each one ships, those screens keep their `useApi` implementation.

**Canonical-archetype list screens defer browser-tier route-mount tests (Epic 11 retro A-4 Option b).** In favour of loader-unit + Playwright E2E. Precedents: 9.1 (deployments), 9.4 (definitions), 10.1 (instances), 11.1 (tasks), 12.1 (jobs). Spec authors should NOT ask for browser-tier `describe(..., ...)` route-mount tests on canonical-archetype list screens — the per-spec deferral note is unnecessary now that the pattern has 5 applications. The harness to render a TanStack Router route with loader + search-param context + `RouterProvider` is intentionally not built; when a non-archetype list screen needs it (likely Epic 18's keyboard navigation), build the harness then. ### Vite → nginx → Flowable proxy chain

[vite.config.js](vite.config.js) proxies `/flowable-rest` → `http://localhost:8080`. The nginx container ([docker/nginx.conf.template](docker/nginx.conf.template)) listens on :8080 and forwards to the `flowable` container while injecting CORS headers. Without nginx in the middle, Flowable's REST app would reject browser requests. The Vite proxy avoids same-origin issues during dev. The allowed CORS origin is parameterized via the `ALLOWED_ORIGIN` env var (default `http://localhost:5173`); the official nginx image renders the template at container start (`/etc/nginx/templates/*.template` → `/etc/nginx/conf.d/*.conf`, envsubst scoped to `ALLOWED_ORIGIN` via `NGINX_ENVSUBST_FILTER`).

`bpmn-js` and `dmn-js` are pre-bundled via `optimizeDeps` and split into their own chunks (`bpmn`, `dmn`, `react`) by `manualChunks`.

### Design system (3 looks × 2 themes × 3 densities)

The stylesheet lives under [src/styles/](src/styles/) — a three-file split totalling ~32KB: [tokens.css](src/styles/tokens.css) (every `:root` / `html[data-look]` / `html[data-density]` variable block), [components.css](src/styles/components.css) (every class hook + `@keyframes` + scrollbar + modeler chrome), and [index.css](src/styles/index.css) (the entry point — `@import` tokens, inline global resets, `@import` components). The split landed in Story 17.1 (atomic `chore(refactor):` — verbatim preservation per ADR-005; no rename of any variable or class hook). There is no Tailwind, CSS Modules, or component library. All theming is driven by **data attributes on `<html>`**:

- `data-look="editorial|terminal|industrial"` — typography + accent character
- `data-theme="light|dark"` — background/foreground swap
- `data-density="compact|regular|comfy"` — row heights and paddings

Each combination defines its own `:root` block of CSS variables (`--bg`, `--fg`, `--accent`, `--font-display`, etc.). Components reference these vars exclusively — never hard-code colors.

The [TweaksPanel](src/tweaks-panel.tsx) (Ctrl+Shift+T or palette icon) is a floating dev-time control that mutates these data attributes. It communicates with [app.tsx](src/app.tsx) via `window.postMessage({ type: "__activate_edit_mode" })`.

Accent colors use OKLCH and can be overridden at runtime via the `ACCENT_PALETTES` map in [app.tsx](src/app.tsx), which sets `--accent` inline on `<html>`.

**Pattern P-007 — Theming hooks (Story 17.2 codification).** Three `<html>` data attributes drive all visual theming via CSS variables: `data-look` (editorial / terminal / industrial), `data-theme` (light / dark), `data-density` (compact / regular / comfy). Each combination defines its own block of CSS variables in [src/styles/tokens.css](src/styles/tokens.css) (`--bg`, `--fg`, `--accent`, `--row-h`, `--pad`, `--gap`, ...); components reference these variables exclusively and never hard-code colors. The active selection is persisted to `localStorage` under `flowatch.tweaks.v1` — lazy-read on mount, written on every change via the `useTweaks` hook in [src/tweaks-panel.tsx](src/tweaks-panel.tsx). The Ctrl+Shift+T shortcut and the Topbar palette icon (`data-testid="tweaks-toggle"`) TOGGLE the TweaksPanel via `window.postMessage({ type: "__activate_edit_mode" })`; the `useEffect` keydown handler short-circuits when `e.target` is an `<input>` / `<textarea>` / `<select>` / `[contenteditable]` so typing the shortcut character into a text field doesn't steal it. Browser-default Ctrl+Shift+T (re-open closed tab) is intentionally overridden when the app has focus — operator-convention, matches the VSCode precedent. New theme tweak keys MUST be added to `TWEAK_DEFAULTS` at [src/app.tsx](src/app.tsx) and consumed by the data-attribute writer effect; the localStorage round-trip is transparent (the `useTweaks` merge-over-defaults shape drops unknown stored keys and lets newly-added defaults take effect on first load after upgrade). The panel container exposes `data-testid="tweaks-panel"` for E2E visibility assertions; the panel's open/closed state is intentionally NOT persisted (every reload starts closed — operator-feel default for a dev tool).

**Pattern P-008 — Token-contract guard test (Story 17.3 codification, Story 17.5 reapplication, Story 18.2 third application, Story 18.4 fourth application).** When a canonical project surface (CSS tokens, an exported `const` registry, a JSON config file) carries invariants that should hold for every entry, write a Vitest test that parses the canonical source and asserts the invariant in a loop. Four applications today: [src/__tests__/wcag-contrast.test.ts](src/__tests__/wcag-contrast.test.ts) parses [src/styles/tokens.css](src/styles/tokens.css) and asserts WCAG AA contrast for 24 colour pairs across 8 look × theme combinations; [src/__tests__/empty-states-exhaustiveness.test.ts](src/__tests__/empty-states-exhaustiveness.test.ts) parses [src/lib/empty-states.tsx](src/lib/empty-states.tsx) via `Object.entries` and asserts title/body/cta invariants for every `ScreenKey`; [src/__tests__/sr-only-class.test.ts](src/__tests__/sr-only-class.test.ts) parses [src/styles/components.css](src/styles/components.css) and asserts the six load-bearing `.sr-only` declarations (Story 18.2); [src/__tests__/shortcuts-exhaustiveness.test.ts](src/__tests__/shortcuts-exhaustiveness.test.ts) parses [src/lib/shortcuts.ts](src/lib/shortcuts.ts) and asserts keys / label / category / scope / no-collision invariants for every `ShortcutKey` (Story 18.4). Per CLAUDE.md "Never extract at N=4", N=4 codifies the no-extraction policy — each consumer remains a small explicit Vitest test parsing its canonical source. Shape: inline helpers over new dependencies (17.3 uses ~50 LOC of OKLCH→sRGB + WCAG luminance inline rather than adding `culori` / `colorjs.io` / `axe-core`); a structural parser that's robust to formatter wrapping (17.3's `parseTokenBlock` uses `[\s\S]+?` + whitespace-collapse so biome's multi-line CSS reformat doesn't break the test); an `EXCEPTIONS` escape hatch (17.3 shape) for documented per-entry deviations with `{ look, theme, pair, minRatio, reason }`. Future invariants — focus-ring contrast at 3:1, toast-template catalogue, sidebar-help blurb registry, error-message catalogue — inherit this template directly. When the canonical source is a TypeScript registry rather than CSS, combine the test with a `satisfies Record<KeyUnion, EntryType>` clause at the registry source (17.5 shape) — the `satisfies` clause is the compile-time guarantee and the P-008 test is defense-in-depth.

**`.sr-only` utility class + status-pill prefix discipline (Story 18.2 codification).** [src/styles/components.css](src/styles/components.css) ships the WebAIM-canonical `.sr-only` utility (`position: absolute; width: 1px; height: 1px; padding: 0; margin: -1px; overflow: hidden; clip: rect(0,0,0,0); white-space: nowrap; border: 0;`) — visible to assistive technology, invisible visually. Every status badge (`<span className="badge" data-tone="ok|warn|bad|mute|neutral">`) carries a leading `<span className="sr-only">Status: </span>` (or domain-appropriate prefix: `Count: ` / `Type: ` / `Group type: ` / `HTTP status: `) so the colour-coded `data-tone` token is accompanied by text-equivalent context. Pattern P-008 guard ([src/__tests__/sr-only-class.test.ts](src/__tests__/sr-only-class.test.ts)) asserts the six load-bearing declarations stay intact — a future widening of the class (e.g. setting `display: none`) breaks the test. New status / count / type badges MUST inherit the convention; new sr-only-equivalent surfaces (form-error `aria-describedby` captions, hidden-but-AT-readable instructions) reuse the same class.

## BMAD planning artefacts live in a private companion repo

`_bmad/` and `_bmad-output/` at the repo root are **symlinks** into the private companion repo [syalioune/flowatch-bmad](https://github.com/syalioune/flowatch-bmad). The split keeps PRD / architecture / epics / story-specs / custom skill overrides off the public OSS surface while letting BMad skills resolve their planning context transparently.

- **Onboarding:** [scripts/setup-bmad.sh](scripts/setup-bmad.sh) (`-d <path>`, `-i` auto-install) clones the private repo and creates absolute symlinks. Re-run if the private checkout moves.
- **Commit sync:** [scripts/bmad-sync.sh](scripts/bmad-sync.sh) is the single chokepoint that commits + pushes the private repo. It **derives the private-repo path from the `_bmad` symlink at runtime — never hardcode `flowatch-bmad`** in any script or hook; resolve via `dirname $(realpath _bmad)` like `bmad-sync.sh` does.
- **`on_complete` directives:** every artefact-producing skill's `_bmad/custom/<skill>.toml` ends with an instruction to run `bash scripts/bmad-sync.sh -m "<conventional-commits message>"`. When writing new override files or extending existing ones, follow that pattern — the agent composes the message from the actual diff.
- **Stop hook:** `.claude/settings.json` runs `bash scripts/bmad-sync.sh --status-only` at end-of-turn. It prints a one-line reminder if the private repo is dirty; it **never** auto-commits. If the reminder fires and you can write a precise commit message from what just happened, propose calling `bmad-sync.sh -m "<message>"`; otherwise leave it for the maintainer.
- **Public vs private boundary:** the shard adapter writes user-story files into `docs/specifications/user-stories/` — that path is in the **public** repo and is committed manually by the maintainer alongside feature work. The sync script only touches the private repo.

When `_bmad/` is not a symlink (code-only contributors), the sync script silently no-ops. Don't fail end-to-end on its absence.

## Conventions worth following

- **No TypeScript.** All source is `.jsx` / `.js`. Don't introduce `.ts(x)` files without explicit ask.
- **No state library.** `useState` / `useEffect` only. Cross-component coordination uses `window` events (see API log) or prop drilling from `App`.
- **No CSS-in-JS.** Add component CSS to [src/styles/components.css](src/styles/components.css); add new tokens to [src/styles/tokens.css](src/styles/tokens.css); use the existing CSS-variable vocabulary.
- **Live API only.** Don't reintroduce mock fixtures into screens — show `{loading, error, empty}` states from the real `useApi` hook instead. [src/data.js](src/data.js) only holds REST endpoint metadata for the Inspector and PageHead chips.
- **`landing/` is the project presentation page**, not part of the app. It's a hand-authored static HTML+CSS one-pager that deploys to GitHub Pages (PRD FR-F12 / FR-F13). Don't pull `src/`, `vite.config.js`, TanStack Router, or React into it. Don't add CDN references — NFR-9 is enforced by `make landing-check`. Visual tokens come from [src/styles/tokens.css](src/styles/tokens.css) editorial-light-regular — kept in sync by hand, not via build coupling. README.md is the source of truth for project facts; the landing page is a curated reflection. Preview locally with `make landing-preview`.
- **Canvas-integration e2e tests assert computed-style, not just class-presence (Epic 26 retro AI-2).** When a story applies CSS classes to elements rendered by vanilla `bpmn-js` / `dmn-js` (or any future canvas-integration library), Playwright e2e MUST include `getComputedStyle(...)` assertions against the rendered SVG — not only `page.locator(".activity-current")` class-presence checks. Class-presence verifies markup; computed-style verifies visibility. bpmn-js' `BpmnRenderer` sets `stroke` / `fill` / `stroke-width` via inline `style` attributes that ALWAYS win over CSS rules without `!important`; diagram-js' own marker classes (`connect-ok` / `drop-ok`) carry `!important` for the same reason. Story 26.2 closed with marker classes applied and class-presence asserts green, but the markers were INVISIBLE — caught only at smoke (`8f9ea57`). The canonical regression-guard shape lives in [e2e/instance-detail-dual-fetch.spec.ts](e2e/instance-detail-dual-fetch.spec.ts): `await expect.poll(() => canvas.evaluate(el => getComputedStyle(el).stroke)).toMatch(/^oklch\(/)` — assert the design-system token shape (`oklch(...)`), not a literal color value. Future Pattern P-006 viewer consumers (Epic 27 model-versioning, any future audit-replay overlay) inherit this discipline on day one.
- **Sidebar nav-link selectors must be href-based, not strict-regex accessible-name (Epic 24 retro AI-1).** Sidebar `<Link>` items that carry a count badge (`<span className="nav-count">{N}</span>` since `bb6c0dd`) concatenate the badge text into the link's accessible name — `getByRole('link', { name: /^Batches$/ })` matches "Batches" but NOT "Batches 0". Use href-based locators on the Sidebar: `page.locator('a[href="/batches"]')` or `page.getByRole('link', { name: /^Batches/ })` (prefix-only regex). The canonical shape lives in [e2e/sidebar-nav.spec.ts](e2e/sidebar-nav.spec.ts) post-`df07751`. This is NOT a Sidebar-specific quirk — any clickable surface that accumulates text fragments (icon-text + label + count + indicator) will hit the same accessible-name concatenation. Story 18.2 codification's `<span className="sr-only">Count: </span>` prefix improves screen-reader announcement but does NOT remove the badge digits from the accessible name (sr-only spans are still part of name-from-contents). The cascade caught at CI: `df07751` after `bb6c0dd`; local-vs-CI gate divergence is the same class of bug as Epic 26 retro AI-4 (biome local-vs-CI). Future nav-touching stories (Epic 25 `/app-definitions`, Epic 28 OIDC sign-in routes) inherit this on day one.

# Modal Conventions

## Modal focus-restore via triggerRef

**Modal focus-restore via `triggerRef` (Story 10.2).** Modals accept `triggerRef?: React.RefObject<HTMLElement | null>` and call `triggerRef.current?.focus()` on Esc / Cancel / successful submit. Callers pass `useRef` on the trigger button (the menuitem or the explicit Open button); a single `triggerRef` per surface is enough since only one modal can be open at a time. All current modals — [upload-deployment-modal.tsx](../../src/lib/upload-deployment-modal.tsx), [delete-deployment-modal.tsx](../../src/lib/delete-deployment-modal.tsx), [start-instance-modal.tsx](../../src/lib/start-instance-modal.tsx), [cancel-instance-modal.tsx](../../src/lib/cancel-instance-modal.tsx) — use this shape. New modals MUST as well.

## fallbackRef focus-restore for destructive modals

**`fallbackRef` focus-restore for destructive modals whose trigger row is removed by the action (Story 19.2 codification, N=4 cross-domain at Epic 23 close).** Destructive modals whose trigger lives in a row that the action ITSELF unmounts (delete-then-reload pattern) accept `fallbackRef?: React.RefObject<HTMLElement | null>` alongside `triggerRef`. The modal's `restoreFocus()` helper checks `document.contains(triggerRef.current)` and falls back to `fallbackRef.current` when the trigger is detached; if neither is in the document, focus silently falls to `<body>` (the silent-no-op clause is what makes cross-domain transfer painless). N=4 consumers today: `<DeleteVariableModal>` (Story 19.2 — runtime variables panel anchor, `fallbackRef` = `addBtnRef`), `<DeleteUserModal>` (Story 22.2 — identity, `fallbackRef` = `backLinkRef` on the `/identity/users/$id` detail page's "← Back" link), `<DeleteGroupModal>` (Story 22.3 — identity, same `backLinkRef` shape on the group detail page), `<DeleteConnectionModal>` (Story 23.1 — saved-connections, `fallbackRef` = the Manage-connections panel's `Add connection` button — the FIRST consumer to use a panel-button fallback rather than a header / back-link fallback). The fallback-target shape varies by parent route: row-in-list-panel → panel's own primary button (Story 19.2 + Story 23.1); row-in-list-route → detail page's back-link or list header's "New X" button (Story 22.2 + Story 22.3). Per "Never extract at N=4" this paragraph IS the codification, NOT an extraction event — same shape as PUT-with-partial-fields, panel-as-sibling, tab-aware action-verb dispatch. Future consumers (Story 25 BAR delete, Story 28 OIDC client delete) inherit the prop signature + the silent-no-op clause without re-evaluation; do NOT extract a `useDestructiveModalFocus` hook or a base-class abstraction.

## Navigate-on-both vs in-modal-ErrorBox decision

**Navigate-on-both vs in-modal-ErrorBox decision (Stories 10.2 / 10.3).** Two failure-path shapes are codified for modal-driven actions:

- **One-shot destructive** (cancel, delete) — modal closes and a toast carries the outcome regardless of success or failure. The engine is the source of truth; the list view shows the current state of the world. See `CancelInstanceModal` (10.3) called from `/instances/$id` which navigates to `/instances` on both success and failure.
- **Retryable creation** (start, deploy) — failure renders an in-modal `ErrorBox` so the operator can fix-and-resubmit without re-typing. See `StartInstanceModal` (10.2) which preserves the operator's Variables JSON on engine error.

Apply by operator-intent: "stop this" vs "I'm building this". Future task / job stories will encounter this fork — match the recipe.

## Discovery-shape modal

**Discovery-shape modal (Story 18.4 codification).** Some operator-feel surfaces are READ-ONLY discovery affordances opened via a global keyboard shortcut — the canonical example is the keyboard cheatsheet ([src/lib/keyboard-cheatsheet-modal.tsx](../../src/lib/keyboard-cheatsheet-modal.tsx)) opened by `?`. Discovery-shape modals: render no submit / cancel buttons (only a `Close` button with `aria-label="Close <modal-name>"`); open via a global `keydown` handler in [src/app.tsx](../../src/app.tsx) that short-circuits when focus is inside an editable element (mirror the Story 17.2 Ctrl+Shift+T pattern); close via Escape (modal owns its own document keydown listener); focus moves to the Close button on open; render content as a grouped table reading from a `src/lib/<registry>.ts` source-of-truth — never a parallel JSX-only list. The shape is the 5th project-codified modal shape after retryable-creation (Story 10.2), one-shot destructive (Story 10.3), console-shape (Story 15.3), and the add-membership variant (Story 14.3). Future discovery-shape candidates: contextual help system, debugger / trace-replay overview, future power-user palette.

## Modal ARIA convention

**Modal ARIA convention (Story 18.2 codification).** Every modal carries `role="dialog"` (or `role="alertdialog"` for one-shot destructive variants — cancel-instance, delete-deployment, delete-dmn-deployment) + `aria-modal="true"` + `aria-labelledby="<modal-key>-title"` referencing the title element's `id`. The title element MUST have a stable `id` attribute. Screen readers announce `alertdialog` with a higher-priority interrupt than `dialog`; reserve it for destructive confirmations that destroy runtime state or deployed resources. Codified across the 12 existing modals; future modals MUST carry this contract from day one.

## Console-shape modal

**Console-shape modal (Story 15.3).** Some operator-feel workflows are iterative: the operator submits, observes the result, edits the input, and re-submits — all without re-opening the modal. The decision Test execute flow is the canonical example. Console-shape modals: stay OPEN on success (no auto-close); render the result inline BELOW the input section (not a separate modal / page); preserve the input on success AND failure (the operator iterates); use a `Reset` button to clear the input back to its default and `Close` for explicit dismissal with focus-restore via `triggerRef`; persist per-key session state in a module-scoped `Map<key, string>` (NOT localStorage — avoids stale-credential security footguns) so re-opening the modal for the same entity restores the last input; carry an `<EmptyState>`-like result panel sub-state for "no rules matched" / "no output variables" sub-cases. See [src/lib/execute-decision-modal.tsx](../../src/lib/execute-decision-modal.tsx). Future console-shape candidates: Epic 19 variable-edit (if it grows beyond a one-shot operation); any future debugger / trace-replay surface. The shape is the 4th project-codified modal shape after retryable-creation (Story 10.2), one-shot destructive (Story 10.3), and the Epic 14.3 add-membership variant.

## Segmented-control auth/mode picker

**Segmented-control auth/mode picker (Story 21.2 → codified at N=3 Story 28.2).** Some retryable-creation modals + the Settings Authentication tab carry a sub-mode discriminator at the top of the input section. The shape: a `<div role="radiogroup" aria-label="<purpose>">` wrapping two-or-more `<button type="button" className="btn" data-variant={selected ? "primary" : "ghost"} aria-pressed={selected}>` segments with stable `data-testid="<key>-mode-<value>"` (or `auth-kind-<value>` for the auth picker). Mode switch clears mode-exclusive fields and preserves shared fields; the caller owns the `switchKind` clear-exclusive logic. Keyboard: Tab enters the group, Tab again leaves; within-group Left/Right roving tabindex is NOT wired — the `aria-pressed`-on-button (toggle-button semantics) shape pairs with native button focus traversal rather than strict `role="radio"` + `aria-checked`. **The `aria-pressed`-over-`role="radio"` question was re-evaluated at N=3 (Story 28.2) and KEPT** — the extraction is presentational only; the keyboard shape is unchanged and matches every other button-row in the app. Both shapes announce "selected/not selected" correctly under screen readers; the difference is keyboard ergonomics. **N=3 codification (Story 28.2):** the per-kind field group (segmented-control + Basic username/password / Bearer token+help / OIDC issuer/clientId/scopes + the dormancy note) was needed in THREE mount points — `<AddConnectionModal>`, `<EditConnectionModal>` (23.2), and the Settings → Authentication tab (28.2) — so it is extracted to the controlled presentational [src/components/AuthStrategyFields.tsx](../../src/components/AuthStrategyFields.tsx); the Authentication tab was removed in Story 34.1 amendments, leaving `<AuthStrategyFields>` at N=2 active consumers (`idPrefix` namespaces the `id`/`htmlFor` + Basic-field testids; the shared `auth-kind-*`/`auth-bearer-*`/`auth-oidc-*`/`auth-dormancy-note` testids stay constant since only one mount renders at a time). State + `switchKind` stay in each caller (the component is controlled). This is the ONE deliberate Epic-28 extraction; the strategies, dispatcher, and validators stay inline-keep-not-extract per their own N counts. The earlier `<AddAttachmentModal>` Link/File toggle (Story 21.2) remains a sibling consumer of the same `aria-pressed` segmented-control shape but is NOT folded into `<AuthStrategyFields>` (different field set).

## install-auth-strategy dispatcher

**install-auth-strategy dispatcher (Story 28.2 — Authentication tab removed in Story 34.1 amendments).** Story 28.2 originally added a third `"authentication"` tab to the Settings modal; Story 34.1 amendments removed it — auth is now edited via the Edit button in `<ManageConnectionsPanel>` (Connection tab), which calls `updateConnection(id, {authStrategyConfig})` and dispatches `SAVED_CONNECTIONS_CHANGED`. [src/lib/install-auth-strategy.ts](../../src/lib/install-auth-strategy.ts) is the `kind → AuthStrategy` dispatcher — it lives at the lib/app layer, NOT `api.ts`, to avoid the `api ← saved-connections ← api` import cycle; it imports `api` + `saved-connections` + the strategy classes and calls `api.setAuthStrategy(...)`. Story 28.3/28.4 add their strategy import HERE. Fired at two points: app mount (honour the persisted kind at first paint) and the `SAVED_CONNECTIONS_CHANGED` listener in [src/app.tsx](../../src/app.tsx) (re-install on connection switch or auth edit — the former Auth-tab Save firing point was removed in Story 34.1 amendments; auth edits via the Edit button in `<ManageConnectionsPanel>` call `updateConnection()` which dispatches `SAVED_CONNECTIONS_CHANGED`, covering the same install). `basic` installs the live `BasicAuthStrategy`; `bearer`/`oidc` install a `DormantAuthStrategy` placeholder (carries the requested `kind` so `getAuthStrategy().kind` reflects the operator's choice, but produces a Basic header from `api.config()` so a bearer/oidc connection activated before its concrete lands still sends credentials) until Story 28.3 (bearer) / 28.4 (oidc) swap the branch. Per "Placeholder-then-real", the swap PRs drop the dormancy assertions.

## datetime-local local→UTC ISO-8601 round-trip

**`<input type="datetime-local">` local→UTC ISO-8601 round-trip (Story 12.2).** The datetime-local input emits `YYYY-MM-DDTHH:MM` in the browser's **LOCAL** timezone. Wire-level Flowable timestamps are ISO-8601 UTC. The convention: hydrate the input via a `toLocalInputValue(iso)` helper that pads month/day/hour/minute as a 2-digit local-time string; on submit parse via `new Date(value)` (browser reinterprets as local) then `.toISOString()` for the wire. The operator's timezone is implicit; the engine receives UTC. Validate `parsed.getTime() > Date.now()` for "must be in the future" inputs. See [src/lib/reschedule-timer-modal.tsx](../../src/lib/reschedule-timer-modal.tsx). Future stories that edit timer `dueDate`, task due-date (Epic 21), or any ISO-time field should reuse this round-trip — don't reinvent the parsing.

# Cross-Story Sequencing Conventions

## Placeholder-then-real

**Placeholder-then-real (multi-epic pattern).** When a story references functionality that arrives in a later story, ship a `data-testid`-anchored placeholder in the earlier story (e.g. a toast that says "X arrives in Story Y.Z"). The `data-testid` is the swap point — the downstream dev replaces the handler without changing markup. Precedents: 9.1's `data-testid="upload-deployment"` (swapped by 9.2), 9.1's two-Delete-items (collapsed by 9.3), 9.4's `Start instance` toast (swapped by 10.2), 10.1's `Cancel` toast (swapped by 10.3). **The swap PR MUST also drop the placeholder-toast E2E assertion from the earlier story's spec file in the same PR** — otherwise the earlier story's E2E asserts a toast text that no longer fires and CI red-builds until the cleanup commit lands (Epic 10 retro §3.5).

## UX-polish cadence

**UX-polish cadence is opt-in by next story.** Canonical archetype stories ship working `window.confirm()` / native form elements / default styles. The polish story swaps to design-system equivalents. See 9.1 (`confirm()` for delete) → 9.3 (`DeleteDeploymentModal`); `prompt()` on instance detail → 10.3 (`CancelInstanceModal`). Don't preempt polish in the archetype; don't skip polish in the polish story.

## Review-patch-fold vs post-closure-fixup decision matrix

**Review-patch-fold vs post-closure-fixup decision matrix (Epic 12 retro §4.3).** Two defensible shapes for live-engine discoveries that arrive mid-epic: **(a) post-closure fixup commits** — appropriate for *genuine surprises* (engine contract mismatch, missing endpoint, undocumented behaviour); produces bisectable "what was the gap between spec'd and shipped" history; Epic 11's three fixup commits (`89de10f` / `f60756f` / `8c8bd51`) are the precedent. **(b) review-patch fold into originating commit** — appropriate for *scope expansion within original story intent* (the engine exposes additional related actions that the story's intent reasonably covers); produces "story shipped with full real action surface" history; Epic 12's `213bef0` (timer-job namespace absorption) and `eb7e377` (`RescheduleTimerModal` source absorption) are the precedent. Pick deliberately. **Review-patches that ADD files must land all-or-nothing in one commit** — splitting test and source across two commits breaks `git bisect` because the test-only commit fails to compile (Epic 12 retro §3.3).

## Bundled refactor + feature avoidance

**Bundled refactor + feature avoidance for canonical-archetype migrations (Epic 12 retro §3.4).** When a canonical-archetype rewrite removes more than 50 LOC from [src/screens.tsx](../../src/screens.tsx) (or any other legacy file), **split the legacy-removal into its own `chore(refactor):` commit** before the feature commit. Story 12.1 bundled a 155-LOC `<JobsScreen>` deletion into the rewrite commit (`886c76e`); the cost was one less bisectable boundary. Story 13.3 was the first deliberate application of the split (`268eee4` feat + `87b9f98` chore(refactor) — −373 LOC from `src/screens.tsx`); per-commit `npm test` was green on both, bisectability cost was zero. Future canonical-archetype migrations (Epic 14 identity, Epic 15 DMN, Epic 16 modeler rewrite) follow the two-commit shape — one extra commit per migration is the price for durable bisectability.

## LegacyXxxShim transitional-migration pattern

**`<LegacyXxxShim>` transitional-migration pattern for multi-tab screens (Epic 13 retro §4.4).** When a canonical-archetype migration of a multi-tab screen lands one tab at a time, ship a wrapper component (`<LegacyXxxShim>`) that mounts the un-migrated tabs' legacy code with a `type` prop. The migrating tabs route through the canonical archetype; non-migrated tabs route through the shim. The final migration story (or its `chore(refactor):` follow-up commit) deletes the shim alongside the legacy block. See Story 13.1 (introduced `<LegacyHistoryShim>` to keep `?type=variables|tasks|activities` rendering while `?type=instances` migrated) and Story 13.3's `87b9f98` chore(refactor) (deleted both the shim and the legacy `<History>` block). Future candidates: Epic 14 identity (users / groups), Epic 15 DMN (decisions / deployments), Epic 16 BPMN modeler rewrite. The shim is a transitional artefact, never a permanent abstraction.

## Live-engine-walkthrough commit shapes — 3-row decision matrix

**Live-engine-walkthrough commit shapes — 3-row decision matrix (Epic 13 retro §4.5).** Extends the review-patch-fold matrix above to a third category — scope expansion BEYOND original story intent — that the original two-row matrix didn't address:

| Category | Recommended commit shape |
|---|---|
| Genuine bug-fix (engine surprise; spec was reasonable) | Post-closure `fix:` commit (Epic 11 shape) OR fold into originating commit if mid-review (Epic 12 shape) |
| Scope expansion within original story intent | Fold into originating story commit (Epic 12 §4.3) — review-patches that ADD files must land all-or-nothing in one commit |
| Scope expansion BEYOND original story intent (symmetry-completeness, unanticipated engine recipe) | **Standalone post-closure `feat:` commit + DAR-Change-Log append on the most-relevant story** — gives bisectable per-feature history; story-as-shipped matches story-as-spec'd; commit body documents the expansion rationale. Epic 13's `b2713d1` (historic-variables panel mirrors runtime) and `78b323a` (runtime-activities via historic endpoint) are the precedent. |

Pick deliberately when the live-engine walkthrough surfaces output. The "DAR-Change-Log append" step matters — without it, the only forensic record for the scope expansion lives in the standalone commit body, divorced from any story file.

## Bundled mega-polish commits — splitting rule

**Bundled mega-polish commits — splitting rule (Epic 14/15/16 retro F-2).** When a polish PR touches >5 files OR mixes >2 rows of the 3-row decision matrix above, split into per-row commits. Row 1 (genuine bug-fix) and Row 3 (scope expansion beyond intent) MUST NOT share a commit — they have different decay characteristics under `git bisect`. Epic 15's `4824aa5` (3825 insertions across 35 files; Rows 1+2+3 simultaneously: JUEL bug-fixes, wrapper realignment, DTO narrowing, UX uplift, audit enrichment, CSS fixes, E2E seeding) is the anti-pattern precedent — a future `git bisect` for "when did the typed Execute form break?" cannot isolate UX item 4 from the Row 1 bug-fixes. Split the next one even when the operator-review surface produces a temptation to ship "all the fallout at once."

## Post-smoke fixup commits discipline

**Post-smoke fixup commits MUST append to the originating story's DAR-Change-Log in the same PR (Epic 14/15/16 retro AI-3).** The Senior Developer Review (AI) block lock fires at `Status: review → done`; post-smoke fixups land *after* that gate, so the lock provides no enforcement. The discipline is operator-side: every `fix:` / `feat:` / `chore:` commit on `develop` that materially extends a closed story's shipped scope must append a row to that story's Change Log table (`Date | Story | Summary` + commit SHA in parens) before the commit lands. Epic 14/15/16 shipped 8 forensic-gap commits; AI-1 backfilled them retroactively. The next epic batch's retro will escalate to a `.claude/hooks/post-merge.sh` if this discipline isn't held by-hand.

## Sprint-status per-story flip

**Sprint-status per-story flip happens ONLY at epic retro (Epic 21 retro AI-1 codification).** The dev / code-review path commits straight to develop without re-entering the `bmad-sprint-status` skill — `{N}-{M}-*` story keys flip from `ready-for-dev` / `in-progress` → `done` ONLY when `bmad-retrospective` fires its cross-file flip override at epic close. Mid-epic flip-lag (story key shows `ready-for-dev` while the commit is on develop) is the EXPECTED steady state, NOT a regression. The `_bmad/custom/bmad-sprint-status.toml` override suppresses the base-skill risk warning for this case (only `ready-for-dev` + zero matching commits + >14-day-stale last_updated still raises a real stalled-story signal). Epic 13 / 14 / 15 / 16 / 17 / 18 / 19 / 20 / 21 retros all debated automation (post-commit git hook, dev-story `on_complete` flip, Makefile sync target) and each one concluded the cost-benefit didn't justify the maintenance surface. The convention is silence + epic-close batch flip. Operators reading sprint-status see real story counts; the `bmad-retrospective.toml` override handles the flip at the right cadence. If a future epic-batch produces enough stories that the retro flip becomes unwieldy (canonical threshold: >10 stories per epic), revisit this lock and consider automation per the Epic 21 retro AI-1 question matrix.

## DAR-block discipline

**DAR-block discipline is enforced at the bmad-sync chokepoint (Epic 18 retro AI-1).** The Epic 13 retro A-3 (option b) populated-content lock in `_bmad/custom/bmad-dev-story.toml` is **skill-scoped** — it fires inside the `bmad-dev-story` skill flow. Direct-commit paths bypass the skill entirely; Epic 18 shipped 4 stories with empty Dev Agent Record / Senior Developer Review (AI) blocks because the dev path never routed through the lock (Epic 18 retro §3.1 / F-3). The git-scoped complement is [scripts/ci/check-dar-blocks.sh](../../scripts/ci/check-dar-blocks.sh), invoked from [scripts/bmad-sync.sh](../../scripts/bmad-sync.sh) (the single chokepoint for private-repo commits). It refuses to commit any story file whose `Status:` is `review` or `done` while these placeholder strings remain: `(Populated by the dev agent during implementation.)`, `_To be populated by the reviewer after implementation._`, `_To be populated by dev agent._`. The structural guard is `## Dev Agent Record` heading presence — retros, sprint-status, deferred-work, spec-*, milestone-* don't carry it and are auto-skipped. Run `make check-dar` for an ad-hoc audit. Residual gap: a maintainer typing `git -C <private-repo> commit` by hand still bypasses the hook; documented as accepted (the alternative — a private-repo-side `.git/hooks/pre-commit` — would diverge from the project's `scripts/ci/*.sh` discipline and would need bootstrap wiring in `setup-bmad.sh`).

## Bake-commit-after-retro discipline

**Bake-commit-after-retro discipline — calibrated by batch size (Epic 18 retro AI-2).** When a retrospective's action items include CLAUDE.md updates, the bake-commit promise (`chore(docs): bake Epic N retro outputs for Epic N+1`) is **calibrated by batch size, not blanket-applied**: (a) **batches with ≤2 distinct CLAUDE.md concerns** may fold those paragraphs into the next feat commit that exercises the pattern — Pattern P-008's landing inside Story 18.2's `525a8a9` is the precedent; (b) **batches with >2 distinct CLAUDE.md concerns** (e.g. Epic 14/15/16 retro had AI-1 backfill 8 DAR rows + AI-2 splitting rule + AI-3 post-smoke append) keep the `chore(docs):` bake-commit shape so `git bisect "when did concept X get documented?"` lands on a docs commit, not a conflated feat commit. The Epic 17 retro promised a bake commit for a 1-paragraph batch (P-008) and silently folded it — functionally equivalent, structurally inconsistent (Epic 18 retro §3.3 / D-4). Next-retro authors: count the CLAUDE.md concerns in your AI list BEFORE writing the bake-commit promise.

## Spec-authoring discipline: grep-verify every "reused from X" claim

**Spec-authoring discipline: grep-verify every "reused from X" claim (Epic 13 retro §3.3).** When a story's Dev Notes asserts that a helper / component / DTO is "reused verbatim from [src/file.tsx]" or "extracted from [src/file.tsx]", the spec author MUST grep the named file at spec-authoring time to confirm the symbol actually lives there. Story 13.1's spec claimed `fmtMs` was already exported from `src/components.tsx`; the dev discovered it was local to `src/screens.tsx` and had to add the export as a scope-creep task. Lightweight (one extra `grep` per "reused from" claim); prevents the dev from inheriting an inaccurate spec. Apply to every future spec.

## Spec-symmetry discipline

**Spec-symmetry discipline: every runtime/historic, claim/unclaim, start/cancel, add/remove story author runs a symmetry-completeness check (Epic 13 retro §3.2 + §3.7).** When a story touches one half of a paired action surface (runtime variables ↔ historic variables; claim ↔ unclaim; start ↔ cancel; add user to group ↔ remove user from group), the spec author runs an explicit symmetry-completeness check: does the spec address both halves? If not, name the gap in the spec (intentional deferral) or expand scope to cover the symmetric pair. Story 13.1's `<InstanceRuntimePanel>` shipped with nested variables but `<InstanceHistoricPanel>` did NOT until post-closure `b2713d1` — the asymmetry was predictable at spec authoring; the live-engine walkthrough caught what spec review didn't. Future Epic 14 (add/remove user from group), Epic 19 (edit/delete variable), Epic 21 (add/delete attachment), Epic 22 (create/update/delete user) and Epic 25 (BAR upload/delete) all touch symmetric action pairs — flag the symmetry check as an explicit spec-authoring task.

## Discipline-lock authoring

**Discipline-lock authoring: gate on populated content, not block presence (Epic 13 retro §4.6).** When a `_bmad/custom/<skill>.toml` discipline lock is added to enforce "the dev MUST produce artefact X before flipping status," the lock condition MUST be populated-content gating, not string-presence gating. Locks that only check "does the section header exist" are easy to satisfy with placeholder content (`_To be populated…_`). The Senior Developer Review (AI) block lock installed by Epic 12 retro A-3 fired on heading presence and shipped 4 Epic 13 stories with stub-only blocks — Epic 13 retro A-3 (option b) fixes by also failing on N specific placeholder strings. The Dev Agent Record lock (Epic 10 retro A-2) works because each of its 4 required subsections has its own concrete acceptance criterion (Debug Log References / Completion Notes List / File List / Change Log); empty bodies are obvious. Future locks: list the required sub-headers AND the placeholder strings that disqualify them.

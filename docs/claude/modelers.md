# Modelers

## Modelers

The modeler components live in [src/modeler/](../../src/modeler/) as a small directory of sibling files: `BpmnModeler.tsx`, `DmnModeler.tsx` (Story 16.4), and `starters.ts` (shared starter XMLs — `BLANK_BPMN_XML`, `LOAN_BPMN_XML`, `LOAN_DMN_XML`). Both modelers wrap `bpmn-js/lib/Modeler` and `dmn-js/lib/Modeler` directly (not the React bindings). Each component instantiates the vanilla class in a `useEffect`, attaches it to a ref'd `<div>`, and bridges save actions to `api.deployBpmn` / `api.deployDmn`. CSS for the modelers is imported once in [src/main.tsx](../../src/main.tsx) — both `bpmn-js/dist/assets/*.css` and `dmn-js/dist/assets/*.css`.

The BPMN modeler:
- Lists deployed definitions in a dropdown and loads the raw XML via `GET /repository/process-definitions/{id}/resourcedata`.
- The embedded `LOAN_BPMN_XML` literal is the default starter when no real definition is selected; `BLANK_BPMN_XML` is loaded when the user picks "new from scratch".
- Deploys via `api.deployBpmn`, which performs a multipart `POST /repository/deployments` (Flowable rejects JSON-with-base64; the mock-mode shape from earlier no longer applies).

The DMN modeler is similar but its REST calls go to the `dmn-api` sub-app (see API layer note above).

The Upload modal at [src/lib/upload-deployment-modal.tsx](../../src/lib/upload-deployment-modal.tsx) (Story 9.2) is the GUI-driven counterpart to the modeler's Save-and-deploy — both routes ultimately call `api.deployBpmn(filename, xml)`.

## Pattern P-006 — Vanilla bpmn-js / dmn-js wrapping

**Pattern P-006 — Vanilla bpmn-js / dmn-js wrapping (Story 16.1).** The modelers are wrapped via direct vanilla-class instantiation, NOT via the `bpmn-js-react` (or `dmn-js-react`) bindings (per ADR-001). The pattern:

1. The vanilla `Modeler` class is instantiated inside a `useEffect` and attached to a ref'd `<div>` (`containerRef`).
2. Event-bus subscriptions (`selection.changed`, `commandStack.changed`, `element.dblclick`, `views.changed`, etc.) are typed via `diagram-js`'s `EventBus<EventMap>` — with **local payload interfaces** naming the actually-observed fields, since diagram-js doesn't publish BPMN/DMN-specific event payloads. The local interface lives alongside the modeler component (see `SelectionChangedEvent` + `CommandStackChangedEvent` in [src/modeler/BpmnModeler.tsx](../../src/modeler/BpmnModeler.tsx)).
3. The cleanup function unsubscribes ALL handlers + calls `modeler.destroy()` to release WebGL / canvas resources. Wrap the `destroy()` call in try/catch — bpmn-js can throw on already-disposed modelers when React strict-mode double-mounts.
4. CSS for the modeler is imported once in `src/main.tsx` (NOT per-component) — both `bpmn-js/dist/assets/*.css` and `dmn-js/dist/assets/*.css` load at module init.
5. The modeler chrome (toolbar + dropdown + deploy button row) honors `data-density` via CSS variables — `var(--row-h)`, `var(--pad)`, `var(--gap)` — so toggling density in TweaksPanel rescales the chrome WITHOUT remounting the canvas (UX Q-5). Hardcoded pixel values inside `.mod-toolbar` and its children are no longer permitted.
6. Shared starter XMLs live in [src/modeler/starters.ts](../../src/modeler/starters.ts) as named exports — not embedded literals inside the modeler component. `BLANK_BPMN_XML` is the "New from scratch" template; `LOAN_BPMN_XML` and `LOAN_DMN_XML` are the demo defaults loaded when no real definition / decision is selected.

See [src/modeler/BpmnModeler.tsx](../../src/modeler/BpmnModeler.tsx) for the BPMN reference implementation and [src/modeler/DmnModeler.tsx](../../src/modeler/DmnModeler.tsx) (Story 16.4) for the DMN counterpart. The pattern is preserved verbatim through the TypeScript migration (ADR-001) — no shift to React bindings is justifiable for v0.0.2.

## Pattern P-006 consumer N=3 — @bpmn-io/form-js-viewer task forms

**Pattern P-006 consumer N=3 — `@bpmn-io/form-js-viewer` task forms (Story 29.1, FR-23).** The form-js viewer is the 3rd P-006 consumer (after bpmn-js / dmn-js). It wraps the vanilla `Form` class from `@bpmn-io/form-js-viewer` EXACTLY like the modelers: instantiated in a `useEffect` on a ref'd `<div>` (`.form-js-host`), loaded via `form.importSchema(schema, data)` (returns a promise — a malformed schema rejects → in-panel `ErrorBox`, never a blank panel), submit bridged via `form.on("submit", handler)` typed with a LOCAL `FormJsSubmitEvent` interface (`{ data, errors }` — form-js publishes no React-typed payload), cleanup `form.off(...)` + `form.destroy()` in try/catch. CSS imported ONCE in [src/main.tsx](../../src/main.tsx) (`@bpmn-io/form-js-viewer/dist/assets/form-js-base.css` + `form-js.css`); the form-js bundle is its own `forms` Vite `manualChunks` chunk mirroring `bpmn`/`dmn`/`oidc`. Native form-js styling is overridden by Flowatch's `data-look` tokens via `.form-js-host .fjs-container` remapping form-js's own `--color-*` vars to `--fg`/`--bg`/`--accent`/`--line` in [src/styles/components.css](../../src/styles/components.css) (Pattern P-007 — no hard-coded colors). The render branch lives INSIDE the existing `<TaskFormPanel>` (Story 11.3, 2nd panel-as-sibling consumer — NOT a new sibling/extraction). `classifyTaskForm(payload)` ([src/components/TaskFormPanel.tsx](../../src/components/TaskFormPanel.tsx)) discriminates: a NON-EMPTY `components` array → form-js, a NON-EMPTY `formProperties` array → legacy (Story 11.3 renderer kept VERBATIM as the FR-23 fallback), else → "none" empty state. **The length check is load-bearing** — flowable-rest:7.2.0 returns `{ formKey: null, formProperties: [] }` (present-but-empty) for no-form tasks, so a bare `Array.isArray` check wrongly classifies no-form tasks as `legacy` and hides the Complete button (golden-path regression). Both branches submit wire-identically through `api.submitTaskForm` (`/form/form-data`, FR-22) — the form-js `data` object maps to the SAME `{ properties: [{ id, value }] }` envelope via `mapFormJsData` (`Object.entries(data).map(([id, value]) => ({ id, value: String(value) }))`); NO new endpoint. **COMPAT BOUNDARY:** the default image has no REST path that returns a `components` array (`/form-api/*` is 404, compat.md), so the form-js branch is **fixture-verified** (unit + a `page.route`-injected e2e fixture in [e2e/task-form-js-render.spec.ts](../../e2e/task-form-js-render.spec.ts)) and DORMANT against `make stack` by design — a live form-js render needs an alternate image or a future embedded-form read path (deferred-work). Do NOT fake a live form-js render the default engine can't produce.

## Flowable BPMN properties panel — moddle descriptor + element-type field dispatch

**Flowable BPMN properties panel — moddle descriptor + element-type field dispatch (Story 30.1, FR-38 / D-8 / ADR-006).** The BPMN modeler's `.mod-props` panel exposes Flowable element extensions as editable fields backed by a registered moddle descriptor. Two load-bearing halves: **(1) the descriptor = round-trip completeness.** [src/modeler/flowable-moddle.json](../../src/modeler/flowable-moddle.json) (name `Flowable`, prefix `flowable`, uri `http://flowable.org/bpmn`) is authored from the canonical [flowable-bpmn-extensions.xsd](https://raw.githubusercontent.com/flowable/flowable-engine/refs/heads/main/modules/flowable-bpmn-converter/src/main/resources/org/flowable/impl/bpmn/parser/flowable-bpmn-extensions.xsd) and registered via the ONLY constructor change — `moddleExtensions: { flowable: flowableModdle }` in [BpmnModeler.tsx](../../src/modeler/BpmnModeler.tsx). It types the FULL extension surface (UserTask/ServiceTask/ScriptTask/CallActivity/BusinessRuleTask/Process attrs + `ExecutionListener`/`TaskListener`/`Field`/`In`/`Out`/`FormProperty` children) so EVERY `flowable:` attribute + extensionElements child round-trips losslessly — the Camunda-Modeler differentiator (Camunda drops Flowable extensions on import→export; Flowatch doesn't). Untyped/foreign content still round-trips via moddle's lax `$attrs` handling, so the descriptor needn't be exhaustive for completeness — it must only type what we surface as fields (proved in [src/modeler/__tests__/flowable-moddle.test.ts](../../src/modeler/__tests__/flowable-moddle.test.ts) via `bpmn-moddle` headless — the full Modeler needs SVG surfaces jsdom lacks). **(2) the fields = editability.** Which fields render is an INLINE `switch`-style dispatch on `bpmnKind(sel)` at the panel render site (CLAUDE.md tab-aware dispatch — NOT a `useElementProperties` hook / field-registry abstraction). Simple attrs read via `bo.get("flowable:<attr>")` and write via `modeling.updateProperties(el, { "flowable:<attr>": value || undefined })` (empty/false CLEARS — never writes `""` or `"false"`; Flowable booleans are string `"true"`/absent). Nested extensionElements (listeners, field injection, in/out) use `bpmnFactory.create` + `modeling.updateModdleProperties` through the command stack (undo + dirty for free — NEVER mutate `businessObject.extensionElements` directly). Each field carries `data-testid="bpmn-prop-<attr>"` + a `mono` wire-attribute label (operator-feel label up top, wire attr in `<span className="mono">`). The listener / field-injection / in-out editors are reusable presentational sub-components (`<ListenerEditor>` etc.) — the field-cluster widget, NOT the kind dispatch. Story 30.1 removed the `bpmn-properties-pending-banner` placeholder (placeholder-then-real). `bpmn-moddle` has no published types — [src/modeler/bpmn-moddle.d.ts](../../src/modeler/bpmn-moddle.d.ts) is a minimal ambient shim (ADR-001 `any` zone). Asserts XML OUTPUT not CSS-class-on-SVG, so the Epic 26 AI-2 computed-style canvas discipline is N/A (noted in the e2e). **There is intentionally NO DMN moddle descriptor (Story 30.2): Flowable's DMN converter consumes standard OMG DMN — it ships zero `flowable:`-namespace extensions; inventing one would type nothing real and risk round-trip corruption.**

## DMN properties surface — no Flowable extensions, standard-metadata + JUEL discipline

**DMN properties surface — no Flowable extensions, standard-metadata + JUEL discipline (Story 30.2, ADR-006 DMN half).** Documented negative finding (AC-1): the Flowable DMN XML converter consumes **standard OMG DMN** — its parser schema directory ([flowable-dmn-xml-converter/.../parser](https://github.com/flowable/flowable-engine/tree/main/modules/flowable-dmn-xml-converter/src/main/resources/org/flowable/impl/dmn/parser)) contains only `DC.xsd` / `DI.xsd` / `DMN12.xsd` / `DMN13.xsd` / `DMNDI12.xsd` / `DMNDI13.xsd` / `dmn.xsd` (all targeting `http://www.omg.org/spec/DMN/20151101`); there is **no** Flowable-specific DMN namespace analogous to BPMN's `http://flowable.org/bpmn`. So 30.2 is a verify-and-document story, NOT a 30.1-style rich-field-editor: dmn-js's built-in `definitionPropertiesView` + decision-table editor already edit the standard surface (decision id/name, hit policy, aggregation, input/output `typeRef`, JUEL rule entries) and round-trip it losslessly (standard content + the generic OMG `extensionElements` escape hatch — proved headless in [src/modeler/__tests__/dmn-roundtrip.test.ts](../../src/modeler/__tests__/dmn-roundtrip.test.ts) via `dmn-moddle`, and live in [e2e/dmn-properties.spec.ts](../../e2e/dmn-properties.spec.ts)). Do NOT invent a `flowable:` DMN descriptor — it would type nothing real and risk corrupting the round-trip. **JUEL-not-FEEL (RC-13):** Flowable DMN cell expressions are JUEL, never S-FEEL — any expression-language affordance must read JUEL. A Pattern P-008 guard in `dmn-roundtrip.test.ts` parses [DmnModeler.tsx](../../src/modeler/DmnModeler.tsx) and asserts no `FEEL` literal is introduced (excluding the project's "operator-feel" UX term), protecting RC-13 against a future "fix FEEL labeling" regression.
